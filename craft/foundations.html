Foundations

Composition, grid, typography, color and contrast, Gestalt, accessibility - the base layer everything else sits on.

Design fundamentals concept map

Composition and layout

  • Scale signals importance; use no more than about 3 sizes per view (one display, one body, one small). (source)
  • Visual hierarchy: guide the eye through scale, value, colour, spacing and placement; squint test to check it.
  • Balance: symmetrical = calm/static, asymmetrical = energy/movement, radial pulls the eye to centre; visual area matters, not element count.
  • Contrast: juxtapose unlike things (size, colour, weight, density, motion) to signal difference; do not de-emphasise text below AA contrast.
  • Gestalt: proximity, similarity, continuation, closure, common region, figure/ground, symmetry. Group by proximity and spacing instead of boxes or grey lines; the gap between groups must clearly exceed the gap within groups.
  • Rule of thirds: put the focal element on one of the four intersections of a 3x3 grid, or divide edges on a third line; gives direction and tension vs dead-centre. Eye-tracking gives some support but it is a starting point, not a law; symmetry, the Gutenberg diagram and the golden ratio each win in places. Web use: headline block in the left third, image in the remaining two thirds; store one focal point per image so every crop keeps the subject on a third line. The 0.618 and 0.667 lines are close; either works. (source)
  • Grid and alignment: 12 columns, consistent margins, align to few strong edges, break the grid on purpose (bleed, overlap); alignment creates unity.
  • Rhythm/repetition, unity/variety: repeat spacing, radius, type steps and one motif; vary scale or density at chosen moments so the page has pacing.
  • Negative space: gaps are structure; luxury reads as fewer elements with resolved spacing. (source)
  • A golden-ratio-derived spacing scale (4/8/16/24/40/64/104/168, ratio ~1.618 from 64) is the author's construction.
  • Proportion and the golden ratio: an aid, not a law; verified details live in #golden-ratio. (source)

Color

  • Radix 12-step scale roles: steps 1-2 app/subtle backgrounds, 3-5 component backgrounds (normal/hover/active), 6-8 borders and focus rings, 9-10 solid accent and hover, 11 low-contrast text, 12 high-contrast text. Build one accent scale this way; step 9 is the accent. (source)
  • 60/30/10 colour rule: 60% dominant background, 30% structural (sections, containers, nav, borders), 10% accent (CTA, active states, key labels); one intentional accent, never multiple unrelated accents.
  • Contrast minimums (WCAG): 4.5:1 normal text and 3:1 large text for AA; 7:1 for AAA; 3:1 for UI components and graphics. Large = 18.66px bold or 24px. Thin light fonts can fail on black due to anti-aliasing. (source)
  • Dark UI: on pure black avoid pure-white body text (use ~92% white), put glow behind the accent, avoid heavy shadows.

Typography

  • Butterick's key rules: body 15-25px on web, line spacing 120-145%, line length 45-90 characters, professional fonts over system/Arial, minimal bold/italic, all caps only under one line with +5-12% letterspacing, kerning on, curly quotes, centred text sparingly. (source)
  • Hierarchy: contrast weight and size, not colour alone; use only 2-3 levels in practice. The 80-160px display sizes are a common studio convention, not a figure from a cited web source.
  • Pairing: one expressive display + one neutral functional sans (not Inter/Poppins/Montserrat by default); contrast in structure, harmony in mood. Typewolf lookbooks are a paid product (12 pairing palettes, 2-3 families each incl. three free Google Fonts options); the free parts (typewolf.com/google-fonts, recommendations) remain useful for pairing study. (source)
  • Fluid type: define scales for a small and a large screen, let the browser interpolate by viewport width with clamp. (source)

Imagery, icons, branding, story

  • Decorative "feel-good" images are ignored in eye-tracking; photos of products, real people (not stock models) and information-carrying images are scrutinised. Big photos work when users request them (zoom, detail). On personal sites users want to see the owner. Rule: every image must carry information or identity; a single hero image may be atmospheric only if it IS the concept. (source)
  • One art direction for imagery (light, grade, crop); original over stock; optimise (AVIF/WebP, sized, lazy except hero).
  • Icons: one set, one stroke weight and corner style; fewer icons (an icon in every card is an AI-slop tell). Lucide is ISC-licensed, Phosphor core is MIT (free commercial).
  • Branding first: colour, type, shape language, voice, motion personality, audience; write a brand brief before building.
  • Storytelling: scroll as chapters with a beginning, tension, peak and end; each section one idea. Verified scrollytelling patterns are collected in the storytelling part of the Building section.

Motion principles

  • Purposeful, fast, ease-out, one orchestrated moment, honour prefers-reduced-motion.

UX laws

Source for the laws themselves: https://lawsofux.com/. Application notes below are the author's synthesis. - Aesthetic-Usability (pretty reads as usable); Hick/Choice Overload (fewer options, faster decisions: few nav items, one primary CTA); Fitts (bigger/closer targets); Jakob (follow familiar patterns for nav/forms, innovate in visuals); Miller (chunk content, don't rely on 7 items); Doherty (respond under 400ms); Peak-End (design a strong peak and a clean ending/CTA); Serial Position (key items first and last in nav/lists); Von Restorff (the one different element is remembered: the accent CTA); Zeigarnik (progress hooks scroll); Pareto (cut sections); Tesler (hide conserved complexity); Postel (forgiving inputs); Occam; Parkinson.

Accessibility and responsive

  • Accessible baseline: WCAG AA contrast (above), visible focus (Radix step 7 for rings), keyboard nav, alt text, prefers-reduced-motion, semantic HTML.]
  • Responsive: meta viewport width=device-width, initial-scale=1; never disable user zoom (user-scalable/maximum-scale hurt accessibility); images max-width:100% with width/height attributes set (avoids layout shift); layout with flexbox/grid and fr units, not fixed pixel widths; media queries on min-width; cap content max width on large screens; test for horizontal overflow (Lighthouse audit). (source)
  • Attention and scroll: 57% of viewing time is above the fold, 74% in the first two screenfuls, 81% in the first three; over 42% of time in the top 20% of the page; within the first screen, over 65% in the top half. Users scroll when given a reason; signifiers invite scrolling. Rule: the first viewport carries the promise and primary action; strongest content in the first two screens; use a cut-off edge/peek of the next section to signal more. Long scroll-story sites are the exception where scroll itself is the experience. (source)

Type legibility evidence from NN/g

  • Glanceable reading (source): for 1-2 word glances larger, regular-width, uppercase text read fastest (all p<0.01); lowercase needed 26% more time than uppercase, condensed 11.2% more than regular; lowercase + small size is worst. Caveats: isolated words only, not sentences; larger lowercase (4mm) performed about like 3mm caps; mixed case untested. Do not set all-lowercase headings/thin condensed type for glanceable UI. 40% of phone sessions are under 15 seconds.
  • No best font for everyone (source): Garamond highest mean (312 wpm), Oswald 295, Open Sans lowest; but Garamond was fastest for a given user only 48% of the time (Franklin Gothic 59%, mean 271). 35% gap best-vs-worst among legible fonts [headline]. Users read 14% faster in their fastest font than their preferred one, so asking them to pick fails. Reading speed falls about 1.5 wpm per year of age (about 11% slower per 20 years); Garamond, Montserrat, Poynter Gothic helped over-35s more; the wrong font hurts older readers most. Takeaway: designer's taste fonts need checking against an older audience; study covered passage reading only, and real users read about 28% of words. Remainder (font-optimisation solution) unread.
  • Let users scale text: fixed pixel text sizes block enlargement; supports using rem/relative units.

Modern CSS building blocks - MDN pages fetched and read

  • Container queries (source): style a component by its container's size/name/style/scroll-state rather than the viewport. Declare container-type: inline-size | size | normal (optionally container-name), then @container name (width > 700px) {... }; size contains both axes, inline-size only inline. Browser-support line not captured on the fetched text.
  • text-wrap-style (source): balance evens line lengths for short blocks (limit six lines Chromium, ten Firefox) - use on headings; pretty slower, reduces orphans, for body copy; stable keeps earlier lines fixed while editing; avoid-orphans is in the spec but unsupported. Cheap polish for hero headlines (anti-slop: avoids one-word last lines).

@layer and:focus-visible

Common region principle

Source: https://www.nngroup.com/articles/common-region/ (Harley 2020; Palmer 1992) - Items within a boundary are perceived as a group sharing a characteristic or function. A border or background color is a strong grouping cue that OVERPOWERS proximity and similarity - use it when whitespace alone can't group (e.g. heterogeneous content, fixed layouts). - Uses: separating chrome from content (Slack's dark sidebar), header/footer regions, image+caption pairing, tabs/accordions connecting label to content, zebra stripes uniting table rows (plus whitespace for columns), cards fixing ambiguous proximity (Food Network case). - Caution: borders added out of caution create clutter; whitespace alone is preferred when it suffices. Full-width contrasting blocks create FALSE FLOORS that stop scrolling. Before adding a boundary ask: is it needed, or would spacing do it?

CSS-Tricks flexbox + grid guides

Sources: https://css-tricks.com/snippets/css/a-guide-to-flexbox/ (Coyier, updated 2026) and https://css-tricks.com/snippets/css/complete-guide-grid/ (House 2021) - the reference guides; library keeps the cheat-sheet, consult the guides for demos. - Scope rule: flexbox for components and small-scale one-direction layouts; grid for larger two-dimensional page layouts. They compose, don't compete. - Flex axes: main axis follows flex-direction (not necessarily horizontal); main size/cross size change meaning with direction - reason to use logical properties. - Container: display, flex-direction, flex-wrap (nowrap default = items shrink on one line), justify-content (main-axis distribution), align-items (cross-axis), align-content (multi-line only, needs wrap), gap (edge-clean spacing, no first/last-child hacks). - Items: flex-grow (share of free space), flex-shrink, flex-basis ("ideal" starting size); flex shorthand; align-self; order. order/reverse only reorders VISUALLY - screen readers keep DOM order, so don't use order for meaningful reading sequence. float/clear/vertical-align are dead on flex items. - Grid anatomy: container/item, line, track, cell, area. fr = fraction of free space; minmax(min,max); repeat; grid-template-areas string art (each row same cell count; period(s) = empty cell; area lines auto-named foo-start/foo-end); prefer the grid shorthand over grid-template because it also resets the implicit grid (auto-columns/rows/flow); auto-flow + dense for backfill packing; safe/unsafe alignment keywords prevent aligning content into unreachable overflow.

SmolCSS - minimal modern snippets

Source: https://smolcss.dev/ (Stephanie Eckles, ModernCSS.dev) - The intrinsic grid: repeat(auto-fit, minmax(min(100%, var(--min)), 1fr)) - the min(100%,...) wrapper stops overflow in narrow contexts. Flexbox equivalent: children flex: 1 1 var(--min). - Modern centering in two lines: display:grid; place-content:center. - Intrinsic container: width: min(100% - 3rem, var(--container-max, 60ch)); margin-inline: auto (logical property). - Breakout grid: named [x-start]/[x-end] lines, 1fr outer columns collapse to 0, content column gets the minmax priority, only row gap set (column gap would prop the collapsed columns open). - Also covered: responsive padding (clamp), sidebar layout, aspect-ratio gallery, unbreakable boxes, composable card, avatar list (grid overlap), scroll snap, focus/visited styles, document base, transitions, article anchors, list markers.

Every Layout + the Stack

Sources: https://every-layout.dev/ and https://every-layout.dev/layouts/stack/ (Pickering & Bell; the layout pages read free; the full set + generators + custom elements are a $69 product - surfaced per the paid-items rule, not requested) - Philosophy: stop making decisions for browsers - no @media breakpoints, no magic numbers; algorithmic, context-independent layout primitives; 12 composable layouts (Box, Center, Cluster, Cover, Grid, Frame, Reel, Stack...). - Margin is a property of the RELATIONSHIP between elements, not of an element: styling p { margin-bottom } breaks in isolation components (double-space against parent padding, stranded last-child margin). - The Stack fix - style the context, not the element:.stack > * + * { margin-block-start: 1.5rem } (the "owl" selector: margin only where a preceding sibling exists). Recursive variant (.stack * + *) for nested stacks; nest separate non-recursive Stacks for deliberate variant spacing. - Base vertical spacing on the body line-height (1.5) - one line of text is the natural denominator; use that ratio for the modular scale.

Every Layout: the Sidebar

Source: https://every-layout.dev/layouts/sidebar/ - Quantum layout: horizontal vs vertical is decided by the space it is placed in, not by a breakpoint. - Recipe:.with-sidebar { display:flex; flex-wrap:wrap; gap:1rem }.sidebar { flex-basis:20rem; flex-grow:1 }.not-sidebar { flex-basis:0; flex-grow:999; min-inline-size:50% } - flex-basis is subtracted from available space before growth; grow:999 makes the main element eat the rest, squashing the sidebar to its ideal width. - min-inline-size:50% is the container-based wrap trigger: the layout stacks when the main element would shrink to half or less (a sidebar stops being a sidebar then). Container-relative, not viewport-relative. - Adjacent elements equal height by default (align-items:stretch); opt out with align-items:flex-start. - No flex-basis on the sidebar = intrinsic width from its content (e.g. image width). Jen Simmons' term: Intrinsic Web Design - the layout computes about itself; suggestion, not prescription.

Every Layout: the Switcher

Source: https://every-layout.dev/layouts/switcher/ - Flexbox Holy Albatross recipe:.switcher { display:flex; flex-wrap:wrap; gap:1rem; --threshold:30rem }.switcher > * { flex-grow:1; flex-basis: calc((var(--threshold) - 100%) * 999) } - (threshold - 100%) flips sign at the container breakpoint; *999 makes it huge; a negative flex-basis is invalid so the browser drops it to 0 (resilient error handling) and every element grows to an equal share = horizontal. Huge positive basis = each takes a full row = vertical. Switches directly, skipping intermediate wraps. - Use when intermediate states confuse (a wrapped lone item looks "featured"): card sets, numbered steps - keep every element equal on one axis. - Nested children need max-inline-size:100% so long content can't inflate one element past its share. - flex-basis:20rem is a target/ideal, not width:20rem - intrinsic thinking (cite: Zoe Mickley Gillenwater on flex-basis as implicit container query). - Quantity query for robustness::nth-last-child(n+5),:nth-last-child(n+5) ~ * { flex-basis:100% } stacks everything once there are 5+ items.

CSS-Tricks Fluid Typography

Source: https://css-tricks.com/snippets/css/fluid-typography/ (2017, Chris Coyier; Mike Riethmuller's math) - The fluid formula: font-size: calc(min + (max - min) * ((100vw - minViewport) / (maxViewport - minViewport))) - a straight line between two viewport/font-size points; wrap in min/max-width media queries (or clamp) so it never escapes the range. - 2017-era Sass mixin in the article; the article itself now points to the newer "Simplified Fluid Typography" (clamp-based) - treat this entry as the historical math reference, and use clamp/Utopia for new work. - Implementation caution tied to WCAG 2.2 1.4.4: pure vw-based font sizes can resist browser text zoom; always include a rem/em component (as Utopia and SmolCSS clamp recipes do).

Subgrid

Source: https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_grid_layout/Subgrid (baseline since Sep 2023) - display:grid makes only DIRECT children grid items; nested grids are independent and can't align to the parent tracks. grid-template-columns/rows: subgrid makes the nested grid inherit the parent's track sizing (and line names, optionally its own names too; gap inherited, overridable). - Use cases: card grids where inner rows (title, body, footer) must align across cards of different content lengths; form field alignment. The parent area expands to fit the subgrid content. - Pair with the card-component guidance: subgrid solves the "ragged card footers" problem without JS or fixed heights.

CSS logical properties and values

Source: https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_logical_properties_and_values - Layout defined by writing direction, not physical sides: block = perpendicular to text flow, inline = parallel. top/left/right/bottom get flow-relative equivalents (block-start, inline-end...); margin/padding/inset/border/size all have logical forms (margin-inline-start, inset-block, inline-size). - Why it matters even for English-only sites: writing-mode changes (vertical text, RTL translations) keep working without re-authoring; Every Layout and SmolCSS recipes use logical properties throughout (min-inline-size, margin-inline:auto) - read them fluently.

Responsive images: srcset, sizes, picture

Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images - Two distinct problems: resolution switching (same content, different pixel counts) and art direction (different crops/compositions per context). - Resolution switching: srcset with w-descriptors (intrinsic widths, not px) + sizes hints ((media-condition) slot-width pairs, first match wins, last is default; vw allowed, % not). Browser weighs screen size, density, zoom, network and picks the closest larger candidate. Simpler variant for fixed-size images: srcset with x-descriptors (1x/2x), no sizes. - Art direction: <picture> wraps <source media> list + a plain <img> fallback (src + alt REQUIRED as the last child or nothing renders). Never use media in source AND media conditions in sizes together - media is for art direction only. - Why not JS/CSS: the preload scanner fetches images before CSS/JS run - JS switching downloads both images, worse than one. Older browsers ignore the new attributes and use src. - Pair with CLS: always keep width/height attributes on the img (or aspect-ratio) so the chosen candidate has reserved space; pair with LCP: never put the LCP image behind srcset discovery tricks that delay it (fetchpriority high, no lazy-load).

The Elements of Typographic Style Applied to the Web

Sources: webtypography.net/toc, /2.1.2 (measure), /2.2.1 (leading) (Richard Rutter's free CC BY-NC application of Bringhurst; whole site open source; https URLs work, bare http 500'd) - Measure (2.1.2): characters per line. Fixed px boxes let the reader's text-size change wreck the measure; liquid % gives the reader control; em (elastic) preserves the typographer's measure at any text size (avg character ~0.5em, so 33em ~= 66 chars). Modern refinement: the ch unit does this directly (60-70ch measure, cf. SmolCSS container). Philosophy: the reader owns the reading environment - embrace it, don't fix it. - Leading (2.2.1): line-height; named for lead strips between lines of type. 12pt text + 3pt lead = line-height 15pt. Pairs with Butterick's 120-145% rule. - Book status: work in progress, chapters short; use as Bringhurst-by-chapter reference, not a complete text (the full Bringhurst book is not freely available online).

Josh Comeau: pixels vs rems - the strategic-unit mental model

Source: https://www.joshwcomeau.com/css/surprising-truth-about-pixels-and-accessibility/ (May 2025) - It's not px-vs-rem; deploy both. The question: "should this value scale when the user changes their default font size?" Yes -> rem; no -> px. - rem for FONT SIZES always: font scaling (browser default font-size setting) only affects relative units; px font sizes ignore it. Zoom multiplies everything (except vw/vh) but is site-by-site manual labor - not a substitute. - px for horizontal padding/borders: rem padding amplifies the line-length problem at large text sizes (fewer words per line AND shrinking line box); borders thickening with font size makes no sense. - rem for MEDIA QUERIES: reframe breakpoints as "available space", not device class. A user at 32px default font has desktop hardware but mobile-like available space; rem breakpoints hand them the space-optimized layout. (px breakpoints + rem sidebars = sidebar eats the laptop screen.) - em anchors to the element's own computed font size (compound on nesting); rem anchors to root.

Josh Comeau: Understanding Layout Algorithms

Source: https://www.joshwcomeau.com/css/understanding-layout-algorithms/ (Mar 2022, updated Nov 2025) - The mental-model shift: CSS is not a property dictionary, it is a set of layout algorithms (Flow, Flexbox, Grid, Positioned, Table). Properties are meaningless alone - each algorithm decides which properties it implements and what they do. - Classic symptom: z-index "not working". Truth: z-index is not implemented in Flow layout. Flexbox DOES implement it, which is why z-index works on flex items with no position:relative. - display:flex does not put the element in Flexbox - it creates a flex formatting context; the CHILDREN are laid out by Flexbox, the parent stays in Flow. Same for grid. Positioned layout has variants (relative/absolute/fixed/sticky) - mini-algorithms sharing z-index support. - Debugging habit: before writing CSS, ask "which layout algorithm renders this element?" - most "CSS is flaky" moments are algorithm-context mismatches.

A List Apart: A Dao of Web Design

Source: https://alistapart.com/article/dao/ (John Allsopp, Apr 2000) - The founding philosophy of everything the layout section now assumes. New mediums inherit rituals from their parents (early TV = "radio with pictures", voice-overs describing visible scenes); the web's parent is print, and the borrowed ritual is CONTROL - pixel-perfect fixation, fixed font sizes, "pixel mechanic". - The inversion: print's controllability is a LIMITATION of that medium, not a feature. Fixed text size = text the reader cannot enlarge; fixed page = unusable on a train. The web's uncontrollability is its strength. - Adaptability IS accessibility: make pages that adapt to the reader's browser, platform, screen, eyesight - that is the whole job, and W3C's founding promise. - Practical roots of later doctrine: think what pages DO not what they look like; form follows function; separate content from appearance (use <em> not <i> - make explicit what print leaves implicit). - Lineage: Marcotte's Responsive Web Design opens by quoting it; Every Layout's "we are outsiders", intrinsic sizing, and the px-vs-rem rule are its direct descendants.

A List Apart: Responsive Web Design

Source: https://alistapart.com/article/responsive-web-design/ (Ethan Marcotte, May 2010 - the article that named the discipline) - The problem statement: bespoke per-device sites ("an iPhone website", then iPad, then...) is a zero-sum game; devices are facets of ONE experience. - Three technical ingredients: fluid grids (target / context = result for % widths), flexible images (max-width:100%), media queries. - The fourth ingredient is the mindset: progressive enhancement across viewing contexts instead of quarantined device experiences. Flexible alone is not enough - a fluid desktop layout still breaks past its intended range (his demo: <800px stress points); media queries recontextualize, not just shrink. - Responsive architecture metaphor (Fox & Kemp): inhabitant and structure mutually influence each other - the design responds to its rendering context the way smart glass responds to occupancy. - Now note the 2020s evolution: container queries, intrinsic layouts (Every Layout), and fluid type reduce dependence on viewport media queries - same philosophy, better primitives.

Print stylesheets

Source: https://alistapart.com/article/goingtoprint/ (Eric Meyer, 2002 - the classic; principles still current) - One document, media-specific styles: <link rel=stylesheet media=print> (or @media print) kills the "printer-friendly version" duplicate document and its version skew. Marcotte's media-query article cites the same media-attribute lineage. - Recipe that still works: hide navigation/chrome (display:none on menu/sidebar), un-float layout for print (floated elements truncated at page bottom was a real browser bug class; float:none returns to normal flow), width:auto + margin on content, body background:white with content backgrounds transparent (browsers don't print backgrounds by default - never rely on background to convey info), color:black text, serif body font, pt sizes for print. - Modern add-ons (ours, from the same principles): @page for margins, avoid page-break inside figures/tables (break-inside: avoid), and remember print is one of Allsopp's adaptability contexts. - Gap: ALA "To Hell With Bad Browsers" (Zeldman 2001) 404s on two slug attempts.

Progressive enhancement, the original argument

Source: https://alistapart.com/article/understandingprogressiveenhancement/ (Gustafson 2008; named by Champeon & Finck, SXSW 2003) - Graceful degradation vs progressive enhancement is perspective, not technique: GD builds for the best browsers and scraps fall to old ones, tested in the last quarter of the cycle; PE starts from CONTENT and layers capability. The difference is focus: browsers vs content. - Peanut M&M model: content peanut in semantic markup; CSS chocolate coating (serves the middle tier - partial CSS, JS disabled by corporate policy); JavaScript hard shell (unobtrusive, capability-scaled). Each layer fully edible alone. - PE was a direct answer to Berners-Lee universality and feeds straight into Yahoo Graded Browser Support, Marcotte's mindset ingredient and Allsopp's adaptability.

Jeremy Keith, Resilient Web Design ch1: Foundations

Source: https://resilientwebdesign.com/chapter1 - Technologies are imprinted with the ghosts of their past: QWERTY from typewriter anti-jamming, clockwise from northern-hemisphere sundials, 60-minute hours from Sumerian base-60, save icons from shirt-pocket floppy disks. New media inherit tropes before finding their own. - The internet's design values ARE political choices: no centre (routes around censorship, not nukes), and a DUMB network - TCP/IP moves packets without caring about contents, which is what let the web (and email, FTP) ride on top. - The web's killer feature is the humble A element; links are laughably simple vs Xanadu's two-way vision - and that simplicity won. TBL expected HTML to be index pages pointing at real documents; people wrote whole documents in it instead. - The founding decision with the longest shadow: the Line Mode Browser ignores tags it doesn't know. Error-tolerance is the web's original resilience feature.

Keith ch2: Materials

Source: https://resilientwebdesign.com/chapter2 - Both HTML and CSS share loose error handling: unknown tag -> render contents; unknown selector/declaration -> skip it. This is what lets vocabulary grow without version lockstep and lets you use new features before universal support (border-radius case). The whole of CSS is one pattern: selector { property: value; } - simple enough to learn, powerful enough for everything. - The hack era (Siegel 1996): 1px spacer GIFs and TABLE layouts tightly coupled structure and presentation - fast to design, brittle in failure. CSS Zen Garden (Shea) proved separation of concerns: one HTML file, many designs. Loose coupling costs more up front, fails more gracefully. - Material honesty (borrowed from architecture): one material should not substitute for another. TABLEs for layout and bg-image rounded corners are façades that crumble under real usage; CSS presentation is materially honest and lets HTML be honest too. - "Some people will see rounded corners. Others won't. And that's okay." - the first explicit statement that different browsers showing different results is acceptable.

Keith ch3: Visions

Source: https://resilientwebdesign.com/chapter3 - Print design is canvas-in: known page dimensions (Kells' vellum, Swiss grid systems) with order imposed on the constraint. The web removed the known dimensions - and designers answered with a consensual hallucination: 640, then 800, 960px "ideal" fixed widths, changing every few years instead of admitting the unknown. - Tools baked the hallucination in: Photoshop's New-document dialog asks for fixed canvas dimensions; Dreamweaver's WYSIWYG promised "what you see is what everyone gets". All software is opinionated (Culkin: we shape our tools, thereafter they shape us). - Mobile shattered the assumptions (screen size? bandwidth? plug-ins?). First answer was the mobile ghetto m.example.com with UA-string sniffing - a Red Queen's race, against One Web. Marcotte's RWD succeeded where Dao (2000) was rejected because the adjacent possible had arrived: fluid grids + flexible images + media queries, united under a slogan. - Mobile First (Wroblewski) is really content-first: prioritise within constraints, discourage ALL device assumptions. Content-out replaces canvas-in; relinquishing the illusion of control is not relinquishing quality.

Keith ch4: Languages

Source: https://resilientwebdesign.com/chapter4 - Postel's Law (Robustness Principle) is the browser's contract: conservative in what you send, liberal in what you accept. HTML and CSS are DECLARATIVE - describe outcome, tolerate errors. JavaScript is IMPERATIVE - one misplaced character and the entire script stops parsing. That asymmetry is the whole argument. - The migration pattern: solutions born in imperative JS (rollovers, form validation) migrate into declarative languages (:hover, required/type) where they become easier AND more robust. - JS abuse history: Zuckerman's pop-up apology; ad-tech bloat and tracking taught users to block JavaScript. On the web the user has the final say. - The web-app trap: "requires JavaScript" assumes the most fragile layer always arrives. NASA 2015: 3MB of JS to read text, black screen until it parses. "Everybody is a non-JavaScript user until the JavaScript has finished loading... if it finishes loading" (Langridge's failure checklist: request, completion, firewall, ISP interference, CDN, browser support). - XHTML 2.0 died because designers refused draconian XML error handling - then the same industry rebuilt that brittleness with JS-only "web apps". - Category error: the web is not a PLATFORM (controlled runtime, 100% or 0%). It is a CONTINUUM - visitors get 20%, 50%, 90% of what you built. Design for the continuum.

Keith ch5: Layers

Source: https://resilientwebdesign.com/chapter5 - Shearing layers (Brand/Duffy, architecture): site (geological) > structure > skin > services > space plan > stuff. Web mapping: URL/domain (bedrock) > HTML structure > CSS presentation > JS behaviour > content. Each layer loosely coupled to the one below (CSS via selectors, JS via the DOM); slow layers enable the adjacent possible above them. - Progressive enhancement (Champeon & Finck, SXSW 2003): apply each layer according to device capability - "from each browser according to its ability, to each device according to its needs". PE is not designing for the lowest common denominator; it is STARTING there with no ceiling. - dowebsitesneedtolookexactlythesameineverybrowser.com (Cederholm): No. Sameness across a 10-year-old browser and a new device would mean you wasted the medium. - Cutting the mustard (BBC): feature-detect, never browser-detect; if (querySelector && addEventListener) { enhance } - and crucially, NO else branch. - Support vs optimization (Frost): support every browser, optimise for none. Core functionality for everyone, then every browser for itself. Jehl: older-browser support comes nearly free with a qualified codebase. Marquis/Boston Globe: "lots of cool features don't work when JS breaks; reading the news is not one of them."

Keith ch6: Steps

Source: https://resilientwebdesign.com/chapter6 - The three-step process (listed backwards in the text, resolved order): 1) IDENTIFY core functionality, 2) make it available with the SIMPLEST possible web technology, 3) enhance. The x-ray perspective (Filament Group): look through the widgets to the content and find a simple HTML equivalent for each piece. - People don't wake up to scroll and tap; they read, write, share, buy (Saarinen: design the thing in its next larger context). - Worked examples: news (HTML file at a URL; layout itself is an enhancement, applied in media queries); social network (reverse-chrono list + a form is the core; Hijax interception, then WebSockets, then p2p); photo sharing (file input is the core; File API/CSS filters are enhancements); word processor (sharing is free via URLs; TEXTAREA is writing; rich editor, autosave Ajax, offline storage + Service Workers make the NETWORK itself an enhancement). - Technical credit (inverse of Cunningham's technical debt): time spent on the core buys freedom to experiment wildly afterward. PE is permission to use cutting-edge APIs, not a ban. - The process scales: whole service -> individual URL (what is THIS URL's core functionality? send it as HTML, conditionally load the rest) -> individual component (interactive map's core is a text address; nav's core is a list of links; enhancement is a sliding scale, not basic-vs-enhanced two versions).

Keith ch7: Challenges

Source: https://resilientwebdesign.com/chapter7 - Hypertext '91 rejected the web for lacking two-way links; "too simple" is the eternal objection - also raised against CSS layouts (until Wired/ESPN), responsive design (until Boston Globe/Microsoft), and now PE. Simplicity is what scales to adoption. - "Too difficult": only the CORE must work everywhere, so the cost is bounded; duplication can be mitigated with universal JS but is worth paying as technical credit anyway. GOV.UK's shorter version: 1) first, just make it work 2) second, make it work better. Each repeat of the process gets faster (CSS layouts, RWD, PE all followed this learning curve). - Resilience is a hidden mark of quality: users on fast new devices never notice it - which means you can implement it without convincing anyone (Hopper's forgiveness-not-permission; matches Frost ch4). - Tools: every framework encodes a philosophy written by people; the load-bearing question is "does its approach match my philosophy?" Tools should serve the workflow, never dictate it. "When I can make a problem the user's problem or my problem, I'll make it my problem every time." User needs trump developer convenience. - Future Friendly manifesto (2011): acknowledge unpredictability, behave future-friendly, help others do the same. "The best way to be future-friendly is to be backwards-compatible." - Assumption graveyard: 640px monitors, Flash installed, mouse+keyboard, fast connections... replaced by new ones (nobody does THAT on phones, every phone has touch, mobile users are hurried, all phone browsers run JS). Mobile didn't create uncertainty; it revealed it.

Response times: the 3 limits

Source: https://www.nngroup.com/articles/response-times-3-important-limits/ (Nielsen 1993, Usability Engineering ch5; 2014 update; unchanged since Miller 1968) - 0.1s = instantaneous: direct manipulation, no feedback needed beyond the result. 1.0s = flow of thought unbroken; user notices the delay but stays in flow; below this, cursor-change suffices. 10s = attention limit: percent-done indicator + a way to interrupt, and expect reorientation on return; only acceptable at natural task breaks. - Percent-done indicators for >10s operations: reassure the system hasn't crashed, give an expected wait, and give the eyes something to watch (a graphic bar beats a number). 2-10s: true percent-done is overkill (display inertia - flashing changes stress users); use a busy cursor + quiet running counter. Unknown duration: absolute progress (names of items processed), last resort a spinner. - Computers can be too fast: time UI animations to a real-time clock, never to execution speed. - The limits are human-perceptual, not technological: identical for native and web apps, and will outlive the next implementation stack.

Legibility, readability, comprehension

Source: https://www.nngroup.com/articles/legibility-readability-comprehension/ (Nielsen 2015) - Copy survives a cost-benefit analysis in the reader's head; three separate barriers: legibility (can they make out the characters), readability (are the words/sentences easy), comprehension (do the concepts land). - Legibility: reasonably large default size (visual acuity declines with age; teens slouch), high contrast on plain backgrounds, clean typefaces (serif fine on modern screens, handwriting/gothic fonts fail). Test: within-subjects reading-speed comparison; 20% slower than a reference design = poor legibility. Watch for lean-in behaviour in tests. - Readability: short plain words, short sentences (subordinate clauses tax short-term memory), active voice, 8th-grade level for broad consumer audiences, ~12th-grade for educated B2B (this very article scores 11th). Grade-level != writing FOR that grade's students. Score with any formula (Flesch-Kincaid, Fry) - all approximate word+sentence length. - Comprehension: user-centric language, domain terminology for specialized audiences even at readability-score cost, inverted pyramid (conclusion first so subsidiary points have context), minimize memory load between text parts.

web.dev Learn Responsive Design: typography

Source: https://web.dev/learn/design/typography (Jeremy Keith / web.dev, 2021). Fluid responsive type in one module. - Text wraps to the viewport by default (UA styles) - responsive by nature; the designer's job is comfort, not fit: size, measure, leading, and leave room for accents in i18n. - Text size by distance: smaller screens are closer, larger screens farther - scale font-size up at wider breakpoints (html { font-size: 125%..200% } across min-width steps). - Fluid type: never font-size in bare vw (kills user resize). Mix a relative unit so zoom still works: calc(0.75rem + 1.5vw). Then bound it: clamp(1rem, 0.75rem + 1.5vw, 2rem) - min 1rem never below user preference, max 2rem. - Measure: Bringhurst 45-75ch satisfactory, 66ch ideal single column, 40-50 multi-column. No line-length property; cap the container with max-inline-size: 66ch - ch units, never px, so user font scaling adjusts the measure. - Line-height: unitless only (1.5, not 24px) so it scales with font-size. Shorter measure tolerates MORE line-height (66ch at 1.65, 45ch blockquote at 2); large leading on long lines breaks the return sweep. - Web fonts: woff2 only, @font-face, and font loading IS UX (paint speed). Preload with crossorigin even same-origin. font-display: swap = system font then swap in (content shift; mitigate with size-adjust), fallback = short block period then stick with system font. Variable fonts: one file spans weights - bigger than one static file, smaller than many; system-ui increasingly gets variable behavior free.

web.dev Learn Responsive Design: media queries

Source: https://web.dev/learn/design/media-queries (2021). - Media types vs features: @media all is the default; print stylesheets via media="print" on link are legitimate (transparent bg saves ink), but never ship a separate stylesheet per breakpoint - use @media at-rules. - Breakpoints belong to CONTENT, not devices: pick the width where lines get uncomfortably long or the layout breaks (e.g. column-count: 2 at min-width 50em because the measure demanded it), not "iPhone width". Device sizes churn every release cycle. - Text-heavy content: use em (or ch) in media queries so breakpoints track the user's font size; image-based content can use px. - Range syntax: @media (width <= 400px) and @media (50em <= width <= 60em) replace min/max-width pairs; combine height too when the design needs it (min-width: 50em and min-height: 30em so two-column text does not force scroll-down-scroll-back-up on short wide windows). - or/not queries are logically tricky - test them explicitly.

web.dev Learn Responsive Design: internationalization

Source: https://web.dev/learn/design/internationalization (2021). - Logical properties everywhere: margin-inline-start/end, block-start/block-end instead of left/right/top/bottom - one stylesheet then survives RTL (Arabic, Hebrew) and vertical writing modes untranslated CSS-side. Grid and flexbox already think logically; directional keywords are the exception to unlearn. Test with dir="rtl" on html. - lang on html (and inline spans when language switches mid-page) feeds screen-reader pronunciation and search; hreflang on a/link announces the destination's language; both when the link text itself is in the target language ("Deutsche Version": hreflang="de" lang="de"). - Design factors for translation: long-word languages (German) punish narrow columns - allow wrapping/hyphenation; line-height must clear accents and diacritics that English never renders; web fonts need the full character range of target languages; never bake text into images - overlay text with CSS instead or you fork every image per language.

web.dev Learn CSS: the cascade

Source: https://web.dev/learn/css/the-cascade (updated 2025). - The cascade is the conflict-resolution algorithm, 4 stages: (1) position/order of appearance, (2) specificity, (3) origin, (4) importance. Position is the FINAL tiebreak - only consulted when everything else ties. - Origin order least-to-most: UA base styles < local user styles (OS prefs, extensions) < authored < authored !important < local user !important < UA !important. Users win with !important - the cascade is designed to let them. - Importance order: normal < animation < !important < transition. Active animations/transitions outrank normal declarations (a transition beats author !important) because they are mid-change of visual state. - Duplicate-declaration fallback trick: declare the same property twice in one rule (font-size: 1.5rem; font-size: clamp(...)); browsers drop values they cannot parse (no error, no break) so the second acts as progressive enhancement. This is the language's founding error-tolerance at work (Resilient Web Design ch2). - DevTools debug: crossed-out rules lost the cascade; a rule missing entirely means the selector never matched (typo hunt, not specificity hunt). - Note: @layer exists as its own module (cascade-layers), covered separately.

web.dev Learn CSS: specificity

Source: https://web.dev/learn/css/specificity (updated 2025). - Scoring is a triad (A,B,C), not a decimal: A=id-like, B=class-like (class, pseudo-class, attribute), C=element-like (type, pseudo-element). Compare component by component: (1,0,0) beats (0,4,3) - 43 classes never outweigh one id. - Universal selector adds nothing.:not and:is add nothing themselves - they inherit the MOST specific argument (so:is(h1,#id) = (1,0,0)).:where always = (0,0,0) - the reset/library-tool: ship base styles in:where so authors can override with a bare element selector. - Inline style= and !important are NOT specificity: they belong to earlier cascade stages (element attachment / origins). !important only re-enters specificity comparison when two !importants compete. - Practical: keep scores as low as the job allows - every point spent is a point someone else must outbid later. Repeated-class trick (.my-button.my-button = (0,2,0)) works but needing it often means the selectors are too specific; refactor instead. Tie in specificity falls to order of appearance. - Why not to style by #id: an id style is nearly impossible to override without another id.

web.dev Learn CSS: inheritance

Source: https://web.dev/learn/css/inheritance (updated 2025). - Inherited-by-default properties are almost all text/list/table related: color, font-*, line-height, letter-spacing, text-align, text-indent, text-transform, white-space, word-spacing, list-style, border-collapse, cursor, direction, visibility, quotes, orphans/widows. Layout/box properties (margin, padding, border, background) never inherit. - Inheritance flows DOWN only; a value set on body never reaches html. Child computed value = parent's value unless the child or the UA stylesheet says otherwise. - The four keywords: inherit (force parent's computed value - great for exceptions that should track a component, e.g. strong inside.my-component), initial (back to spec default), unset (inherit if inherited-by-default, else initial - the safe generic reset; all: unset nukes everything future-proof), revert (drop back past the AUTHOR origin only - UA/user styles still apply; useful for component resets that keep UA semantics), revert-layer (same but only within the current cascade layer - third-party-in-a-layer + overrides-in-higher-layer pattern).

web.dev Learn CSS: box model

Source: https://web.dev/learn/css/box-model (2021). - Everything CSS displays is a box, even a circle made by border-radius. Four areas: content box -> padding box (background shows through; scrollbars live here) -> border box -> margin box (outline and box-shadow also occupy it - painted on top, never affect layout; a 200px outline changes nothing inside the border edge). - Extrinsic vs intrinsic sizing: setting width/height is extrinsic - you control the box, content can overflow; intrinsic (unset, or min-content/max-content/fit-content) lets content drive the box, overflow nearly impossible. Intrinsic is the browser default and usually the more flexible choice. - box-sizing: content-box is the UA default - width applies to the CONTENT box, so padding+border add on top (width:200px + padding 20px + border 10px renders 260px). border-box applies width to the border box - padding/border push inward. Universal *, *::before, *::after { box-sizing: border-box } is standard in modern resets for predictability. - Display defaults come from the UA stylesheet: div=block (fills inline space), li=list-item, span=inline (block margins not respected by siblings); inline-block keeps inline flow but siblings respect its box.

web.dev Learn CSS: z-index and stacking contexts

Source: https://web.dev/learn/css/z-index (2021). - Default stacking without z-index: document source order - later elements paint on top. - z-index only works on positioned elements (position != static) - the classic "z-index not working" cause. Exception: flex and grid items accept z-index with no positioning. - Stacking context = a group of elements that move on the z axis TOGETHER. Child z-index values are only relative to their parent's context: a child with z-index 999 inside a parent context of z-index 1 still loses to a sibling context of z-index 2. Negative z-index (-1) can only hide a child behind its parent if the parent has not formed its own context (parent z-index auto). - html is a stacking context; nothing ever goes behind it. - Contexts are created by more than position+z-index: opacity < 1, transform, will-change, filter, backface-visibility:hidden - anything that creates a GPU composite layer. Debugging rule: a mysteriously untoppable overlay usually means an ancestor quietly formed a context.

web.dev Learn CSS: flexbox

Source: https://web.dev/learn/css/flexbox (2021). - One-dimensional layout for a GROUP of differently-sized items: give the browser flexible boundaries, not rigid dimensions. Sidebar-inline-with-content that wraps under pressure is the canonical use. - Initial values: flex-direction row, flex-wrap nowrap (overflow at min-content size), flex-grow 0 / shrink 1 / basis auto, justify-content flex-start, align-content stretch, align-self stretch (why a row of items matches the tallest item's height). - Main axis vs cross axis follow writing mode, not screen geometry: row in RTL Arabic starts on the right; vertical Japanese runs rows top-to-bottom. That is why the vocabulary is start/end, not left/right (i18n). - flex: auto (1 1 auto) = grow from max-content, so bigger items stay bigger; flex: 1 (1 1 0) = all items grow from zero, equal sizes; flex: none = inflexible, alignment-only. - Wrapped flex lines are independent containers: nothing in row 2 can align with row 1 - that is the one-dimensional limit; need both axes = grid. - justify-* = main axis, align-* = cross axis; justify-content needs spare space to do anything (in a column direction, the container needs a block-size first). No justify-self in flexbox - items move as a group; split one off with an auto margin (margin-left:auto absorbs space, pushing that item away). - Reordering hazards: row-reverse/column-reverse and the order property change VISUAL order only; keyboard and screen readers follow DOM. Never use order to patch document order - fix the HTML. - Centering: justify-content:center + align-items:center on the container.

web.dev Learn CSS: grid

Source: https://web.dev/learn/css/grid (2021). - Two-dimensional layout: rows AND columns simultaneously - combines extrinsic control with intrinsic flexibility. Terminology: lines (numbered from 1 per writing mode), tracks, cells, areas, gaps (sized like tracks, hold no content), container/item. - Track sizing toolbox: fixed units, auto (= as big as content; stretches to fill spare space by default), intrinsic keywords min-content (narrow as the longest word) / max-content (unbroken string, may overflow) / fit-content(10em) (max-content capped), the grid-only fr unit (share of REMAINING space after fixed tracks and gaps; fr is distributed after layout, like flex:auto). - minmax: minmax(0, 1fr) forces equal shares (without the 0 floor, content minimums skew the shares); minmax(10em, auto) floors a row. - repeat + auto-fill/auto-fit + minmax = the media-query-free responsive card grid: repeat(auto-fill, minmax(200px, 1fr)). auto-fill keeps empty tracks (gap at the end); auto-fit collapses them to 0 so real tracks absorb the space. Identical once the first track fills. (Matches macro-layouts.) - Auto-placement: row flow default, grid-auto-flow: column flips it (writing-mode relative); span n across tracks; dense backfills gaps but disconnects visual from source order (same a11y hazard as flex order). - Line-based placement: grid-column: 1 / -1 spans the EXPLICIT grid only - negative line numbers cannot reach the end of implicit tracks. Implicit tracks auto-size; control with grid-auto-rows/columns. Overlap cells by placing items on the same lines; later source paints on top, z-index adjusts. - Named lines ([main-start aside-start] 1fr...) and grid-template-areas let the layout be read in the CSS itself; named lines are writing-mode aware.

MDN Learn: cascade layers

Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Cascade_layers (living doc). The web.dev Learn CSS course has no dedicated layers module (its inheritance module covers revert-layer) - MDN fills the gap. - Full cascade order (7 steps): relevance -> importance -> origin -> cascade layers -> specificity -> @scope proximity (fewest DOM hops to scope root wins) -> order of appearance. Only survivors of each step compete at the next. - Eight precedence levels: UA normal < user normal < author normal < animating < author !important < user !important < UA !important < transitioning. Specificity is never compared ACROSS origins - author 0-0-0 beats UA 0-1-1 every time; origin precedence is absolute. - Layers are sub-origins inside an origin: creation ORDER sets precedence and cannot be changed later. First layer created = lowest precedence (normal styles). Unlayered styles form an implicit final layer: unlayered NORMAL beats all layered normal (even lower-specificity, earlier unlayered). - !important INVERTS layer order: unlayered important is lowest among important; the FIRST created layer's important styles are the strongest layered ones. So a library in layer 1 can defend with !important; your layer-3 overrides still beat its normal styles. - Precedence stack normal-to-top: layer-1 normal... layer-n normal < unlayered normal < inline normal < animating < unlayered !important < layer-n !important... layer-1 !important < inline !important < transitioning. - Three creation methods: @layer statement (@layer theme, layout, utilities; - declare full order as line 1 of the CSS), @layer block (named or anonymous; anonymous layers can never be referenced or extended), @import "x.css" layer(name) or layer - the only way to layer a third-party file you cannot edit (no link-element equivalent). - Reusing a named block appends to that layer; a bare @layer site, page; re-declaration does NOT reorder existing layers. Layers created inside non-matching media queries do not exist - so layer ORDER can change with viewport size. - Nesting via dot notation (components.narrow) solves library-name collisions: importing a layered stylesheet nests its layers inside yours. - The problem it solves: many teams/frameworks in one author origin escalating specificity wars and !important fixes; layers make precedence explicit without touching selectors.

web.dev Learn CSS: sizing units

Source: https://web.dev/learn/css/sizing (2021). - Unitless numbers: line-height unitless = ratio of computed font-size, survives inheritance (a fixed 15px does not). Also opacity, filter amounts, rgb channels, transform scale. - Percentage gotchas: width % resolves against parent width; margin/padding % resolves against parent WIDTH in every direction (margin-top:50% of a 300px box = 150px, not height-based); transform translateX % resolves against the element's OWN width. - Absolute units (cm, mm, Q, in, pc, pt, px) all resolve against the same base (1in = 96px) - predictable, but physical units only mean physical size in print stylesheets, not on screens. - Font-relative family beyond em/rem: ex/x-height, cap-height, ch (width of "0" - the measure tool, 60ch), ic (CJK full-width glyph advance), lh (line height of the element). r-prefixed = root versions. Use cases: cap/ex for optical alignment, lh for rhythm, ic for CJK layouts. - Viewport units: vw/vh plus logical vi/vb; vmin/vmax. Mobile browser chrome problem: vh lies when the URL bar shows/hides. Three families: lvh (largest, UI hidden = classic vh), svh (smallest, UI visible - the safe full-height hero), dvh (dynamic, tracks UI show/hide - can cause jumpiness). Pick svh for guaranteed-visible content. - Container-relative units: cqw/cqh/cqi/cqb/cqmin/cqmax = 1% of the query container's dimensions - fluid component type inside container queries without viewport coupling (micro layouts). - px for text ignores the user's font-size preference; em/rem honor it. Resolution media feature (min-resolution: 192dpi / -webkit-min-device-pixel-ratio: 2) for Retina image swaps.

web.dev Learn CSS: logical properties

Source: https://web.dev/learn/css/logical-properties (2021). Deepens the i18n module with the full property map. - Vocabulary: block flow = where stacked paragraphs go (top-to-bottom in English); inline flow = how text runs in a sentence (ltr in English, rtl in Arabic). writing-mode changes both per element or document. - Property map: width/height -> inline-size/block-size; margin-top -> margin-block-start; margin-left -> margin-inline-start; top/right/bottom/left -> inset-block-start/inline-end/etc; text-align:right -> text-align:end; shorthands padding-block/margin-inline (two-value forms); border-bottom -> border-block-end; border-bottom-right-radius -> border-end-end-radius (block-end then inline-end). - The icon-beside-label bug: margin-right on the icon breaks in RTL - margin-inline-end is the fix. This is the canonical why-bother example. - vi/vb units: 1% of viewport in inline/block direction - follow reading direction where vw/vh stay physical. - Not only for translation: one ruleset can serve horizontal AND deliberately-rotated UI (a vertical-rl chart axis label takes the same margin-block-start as the horizontal one) - flow-relative thinking makes components more versatile, not just more translatable.

web.dev Learn CSS: focus

Source: https://web.dev/learn/css/focus (2021). - tabindex semantics: 0 = focusable in source order; -1 = script/hash focus only (skip-link targets, deleted-item recovery - matches IC todo list); >0 = hijacks the global tab order - avoid unless forced. -:focus vs:focus-visible vs:focus-within: style keyboard-only focus loudly (3px solid) and share quieter styles between:focus/:hover (matches Learn Design accessibility). - outline + outline-offset: offset adds visual breathing room without changing geometry (unlike padding). - Windows High Contrast Mode trap: box-shadow focus rings DISAPPEAR there (WHCM strips shadows and most background images); outline survives. Never replace outline with box-shadow even though box-shadow clips to border-radius and outline does not. - Never outline:none on anything keyboard-focusable; make the focus state clearly distinct from the default state.

web.dev Learn CSS: transitions

Source: https://web.dev/learn/css/transitions (updated 2025). - A transition interpolates between states instead of snapping - its UX job is cause-and-effect: visual direction and feedback about what the interaction did. - Property by property: transition-property/duration/timing-function/delay; shorthand transition: transform 300ms ease-in-out 0s. Name each property explicitly - transition-property: all causes perf issues and unintended transitions. - Only interpolable properties transition; font-family has no middle state (it "transitions" discretely, i.e. snaps). MDN keeps the animatable list. - transition-delay tricks: stagger a group by rising delay per item; a NEGATIVE delay starts the transition partway through its timeline (debugging tool). - Different enter vs exit: put the slow transition on the base rule and a fast one on:hover - hover-in snaps (150ms), hover-out lingers (2s). The transition on the matching state governs the move INTO that state. - Triggers::hover,:focus,:focus-within,:target,:active, and JS class changes. - transform and opacity are the GPU-accelerated, layout-free properties; transitioning width/height forces layout recalculation per frame for every affected element. Color transitions do not need prefers-reduced-motion gating (judgment call per module). - prefers-reduced-motion patterns: gate with (prefers-reduced-motion: reduce) { transition: none } or the opt-in (no-preference) variant.

web.dev Learn CSS: animations

Source: https://web.dev/learn/css/animations (2021). - @keyframes maps states to timeline positions: from/to = 0%/100%, any number of intermediate percentages (pulse: 0% opacity 0, 50% scale(1.4) opacity 0.4). The rule name is a case-sensitive custom-ident referenced by the animation property. - animation-duration defaults to 0s - the animation runs but is invisible; no negative values allowed. - Keyframes vs transitions: transitions need a state-change trigger and interpolate between two states; keyframe animations are self-running multi-state timelines (the pulsing helper-dot case).

web.dev Learn CSS: overflow

Patterns: what good sites do and why

Luxury / "expensive" feel

Source: https://www.dellamattia.com/journal/web-design-for-luxury-brands-what-makes-the-difference - "Luxury web design is not a dark background with gold text"; it is a level of care: the resolution of decisions (exact weight, size, line height, background; a spacing system where every gap has a reason). - Four levers: (1) image quality and one art-direction logic (light direction, colour temperature, composition); (2) typography with real hierarchy, signature face plus a functional second face, tuned tracking on uppercase labels; (3) load performance (next-gen formats, lazy loading with placeholders, font loading that avoids layout shift); (4) restraint in interaction: movement used "the way a luxury brand uses a logo: rarely, precisely". - Don't: copy LVMH/French fashion-house codes without that brand weight; use stock photography; sacrifice function for form. - Underneath it is trust: consistency, speed, clarity, nothing accidental.

Negative space

  • Whitespace helps balance, scanning and reading; use a consistent spacing system and the proximity principle. (source)
  • Fewer elements per viewport, one focal point, bigger gaps between groups than within groups; this replaces boxes and lines.

Hierarchy

  • Visual hierarchy guides the eye to the most important elements through colour and contrast, scale and grouping (proximity and common regions); the article ends with a squint test. (source)
  • Contrast in value and saturation vs the surrounding context creates hierarchy, not the colour itself; use bright saturated colours for important items, reserve warm bright red for warnings; too many colours of similar value flatten hierarchy.
  • Refactoring UI advice (start with a feature not a layout; design in greyscale, add colour last; limit choices with a defined scale; de-emphasise secondary content):

Golden ratio

  • phi = 1.618. NN/g's text example: 16px body gives a header of 16 x 1.618 = about 26px, and the same multiple can set line height (about 26px for 16px type). (source)
  • NN/g also shows layout and image splits using the golden rectangle; the 61.8/38.2 column split and 1.618fr 1fr in CSS grid are an application of it.
  • Caveat from NN/g: they say "it turns out that things are a l..." (text truncated at source); a full-ratio type scale of x1.618 is huge, so practice uses 1.2-1.333 steps.

Typography

  • Fluid type and space without breakpoints: define scales for a small and a large screen, let the browser interpolate by viewport width (clamp). (source)

Hero

  • One focal object; communicate what, why and action in the first viewport.
  • Hero types: editorial, cinematic, interactive, product-dominant, typographic. Seen examples: Stripe Press (product-dominant, one 3D stack), Aeon article (full-bleed image + serif title), Arcynia (illustration), Empourium (photo framed by hairlines).

Scroll as story

  • Pin and scrub with GSAP ScrollTrigger over Lenis smooth scroll; recipe and sources in the Motion Craft section. One motif repeats; section transitions are designed (colour grade shifts, mask reveals).

Performance and accessibility

  • Core Web Vitals at the 75th percentile: LCP within 2.5s, INP 200ms or less, CLS 0.1 or less. (source)
  • Compress hero media, AVIF/WebP, preload display font, font-display swap with matched fallback metrics, prefers-reduced-motion, keyboard focus states.

Progress and loading feedback

NN/g wait-animation rules (source): - Immediate visual feedback on every action, always (pressed state etc.); without it users re-tap. - Use a progress indicator for anything over ~1s. Looped animation only for 2-10s waits (under 1s it flashes and distracts; over 10s users assume it hung — one test user waited 15 min on a stuck spinner). - Percent-done for 10s+ waits (or multi-record processes with "3 of 50" text). Always add text saying what is happening. - Never fake smoothness: a bar that hangs on the last percent is worse than none; start slow and accelerate (exceed expectations, don't disappoint). Exception: surveys should start fast, end slow (reduces drop-off). - Static "Loading…" text: don't; it can't signal a hang. Don't-click-again warnings: don't.

Empty states

NN/g empty-state guidelines (source): - Never leave a container totally empty: a brief message ("No records for this date range") communicates system status; without it users can't tell empty from loading or error. - Worse than silence is a WRONG status message ("No records" during loading, replaced by content seconds later) — destroys trust; show a loading indicator until truth is known. - Empty states are learning moments ("pull revelations"): say what the area is for and how content gets there (DataDog: "Star your favorites to list them here") — better than forced upfront tutorials. - Give a direct pathway: a button/link that starts the task that populates the empty state ("Create"), not just a description of what's missing.

Forms: labels, placeholders, inline validation

  • Placeholders must not replace labels: 7 NN/g reasons (memory strain, cannot check work, errors unfixable, tab-through irritation, filled fields get skipped, mistaken for autofill, manual delete). Placeholder alongside a visible label is "better" but essential hints still belong outside the field. Default light-grey placeholder fails contrast; not all screen readers speak it. Source: https://www.nngroup.com/articles/form-design-placeholders/ (Sherwin, 2014, reviewed 2018)
  • Floating labels: label sits as placeholder, rises on focus. Saves mobile height and keeps the label visible while typing; still has the "filled field looks pre-filled" and accessibility problems. Same source.
  • Error flow: inline validation where possible; show success only where it helps (username availability, password strength), not on merely-required fields; message beside the field; red/orange/green plus icon (colour-blind safe), tinted field background; no modals except simple errors; do not validate before the user leaves the field; summaries never the only indicator; no tooltips for errors; extra help after repeated errors. Source: https://www.nngroup.com/articles/errors-forms-design-guidelines/ (Krause, 2019, reviewed 2024) - Items 1-7 are covered in full; items 8-10 are listed from the article's contents only.

Icons: labels, accordion signifiers

  • Icons need a visible text label: only home, print, magnifier are near-universal; heart/star/hamburger/clock mean different things per site (a clock for history: zero clicks). Labels never hover-only; a restyled standard icon also needs one. Icons are more salient on phones than on busy desktops. Benefits: big touch targets, compact, brand family. Source: https://www.nngroup.com/articles/icon-usability/ (Harley, 2014).
  • Accordion signifier: caret is the only standard signifier that beat no-icon/nonsense icon at signalling "opens in place"; plus and right-arrow were no better than no icon. Taps split roughly equally between icon and label (29% of caret taps hit the label), so never split-button them. Source: https://www.nngroup.com/articles/accordion-icons/ (Laubheimer & Budiu, 2020).

Carousels / hero rotators

  • Default: prefer one static hero or integrate content into the UI; people scroll past carousels and see only frame one, so one off-message frame misrepresents the brand. Source: https://www.nngroup.com/articles/designing-effective-carousels/ (Pernice, 2013, reviewed Aug 2026).
  • If you must: <=5 frames; crisp text/images; show count and position (a subtly larger dot fails); distinct, recognisable controls inside the carousel (dots are a poor mobile cue); big targets and visible arrows on busy backgrounds; "bleed" the next frame to signal more.
  • Auto-forward: avoid on mobile, avoid for ad-like content; if used, time at about 3 words per second, loop, keep the selected frame shown; animated ads were looked at 27% of the time in NN/g eyetracking.
  • Ties to reduced motion : auto-advance must stop for reduce, and WCAG pause control applies.

Keyboard focus

  • 2.4.13 Focus Appearance (source): focus indicator area at least a 2 CSS px thick perimeter of the component, and 3:1 contrast between focused and unfocused pixels; exceptions when the browser default is untouched. Glow/shadow outside the component does not count toward the perimeter. Conformance level not stated on the fetched text.
  • C45 technique (source): style :focus-visible (browsers show it for keyboard, usually not for mouse, except text inputs); best practice also keep a :focus style for pointer users who benefit. Techniques are examples, not requirements.
  • Never outline: none without a replacement; the default is exempt only while untouched.

Keyboard focus, part 2 - closes the above

  • 2.4.7 Focus Visible (source): some mode of operation must show focus; indicator must not be time-limited; it counts as non-text content so 1.4.11 Non-text Contrast (stated AA on the page) applies.
  • 2.4.11 Focus Not Obscured (Minimum) (source): a focused component must not be entirely hidden by author-created content (sticky headers, cookie bars, bottom sheets); exception if the user can reveal it without moving focus.
  • 2.4.1 Bypass Blocks (source): a way to skip repeated blocks (nav, header, ad frames); skip link is the usual means; structural markup (1.3.1) also helps; not needed for a nav placed at page bottom.

Status trackers

  • Tracker = pull (user checks), progress update = push (notification). Offer both: tracker alone breeds obsessive checking, notifications alone fail on wrong contact details.
  • Put the latest update first and prominent; keep related links visually distinct; vertical logs/bars suit mobile and long update lists; newest on top with date/time.
  • Plain language, no backend jargon ("label created"); scannable rows with dated headers and generous columns; tell users what reference they need; specific login errors.

Forms, part 2: top-10 and mobile input checklist

  • Web form top 10 (source): keep it short; group label+field (label above for mobile/short forms); single column (short related fields like city/state/zip may share a row); logical sequence; avoid placeholders; match field type and size to input (radios not dropdowns for 2-3 options; field width fits value); mark optional fields (limit to 1-2); state format rules up front; no Reset/Clear buttons (Cancel, visually weaker, for sensitive forms); errors high-visibility and specific, not colour alone (outline + red text + heavier weight), keep the user's input. Cites Seckler et al., CHI 2014: guideline-following forms roughly halve error rate on first submit (exact figures not confirmed).
  • Mobile input checklist, 14 items (source): is the field needed; label above (not inside/below); required/optional marked; no placeholder; field wide enough; visible with keyboard in both orientations; defaults/history; use phone features (camera, GPS, voice, contacts); compute from other input; allow paste; right keyboard type; autocomplete but no autocorrect on names/addresses/emails; tolerate typos/abbreviations; accept any format and autoformat.

Skeleton screens

Source: https://www.nngroup.com/articles/skeleton-screens/ (Tankala, 2023, reviewed Sep 2026). Extends the progress-indicator entry above. - Types: static wireframe boxes (most common; teach the page structure and hierarchy), animated shimmer/pulse (reassures, but can distract or hurt accessibility - honour reduced motion), frame-only (header/footer, no content wireframe) - NOT recommended, equivalent to a blank spinner. - Use for full-page loads under 10s; spinner for a single module (a card, video) 2-10s; progress bar for 10s+ or processes (upload/convert); nothing for loads under 1s (a flash feels hectic). - Benefits: stops "is it broken" abandonment, shorter perceived wait, lower cognitive load via early mental model. Not a substitute for real performance work (see Core Web Vitals).

Image alt text decision tree

Source: https://www.w3.org/WAI/tutorials/images/decision-tree/ - Text in image also present as real text, or only visual effect: empty alt. - Icon/image in a link or button: alt states destination or action, not the picture. - Meaningful photo/simple graphic: brief description conveying the meaning. - Chart/complex info: put the information elsewhere on the page. - Purely decorative (hero textures, ornaments): empty alt (or CSS background). - Text only in image: alt carries that text; prefer real web fonts.

Native dialog element

Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog - Baseline widely available since March 2022. Open with showModal (modal) or show (non-modal), not the open attribute. - closedby: any (light dismiss + Esc + custom), closerequest (Esc/back + custom), none. showModal defaults to closerequest; otherwise none. closedby has limited support, so verify before relying. - Never put tabindex on dialog.

Popover API

Source: https://developer.mozilla.org/en-US/docs/Web/API/Popover_API - Baseline newly available since Jan 2025. Always non-modal; use dialog for modal. - Markup: button popovertarget="id" + element with popover attribute. Uses: menus, toasts, suggestions, pickers, teaching UI. - Pairs with CSS anchor positioning for tooltips/menus without JS.

Icon design tips - detail deltas

Source: https://www.nngroup.com/articles/icon-usability/ (Harley, 2014) - 5-second rule: if you cannot think of a fitting icon in 5 seconds, no icon will communicate that meaning. - Test icons twice: recognizability (ask strangers what they mean) and memorability (ask users weeks later if they remember). - Relative size: a hamburger at 20-25% of a mobile header width stays the same pixel size on desktop and gets lost; mobile icon choices do not transfer up. - Words vs icons: text labels suffer read-tap asymmetry on touch (small read size, small tap target); icons make better targets. - Tognazzini: "a word is worth a thousand pictures."

WAI form labels

Source: https://www.w3.org/WAI/tutorials/forms/labels/ - Always use label with for/id matching. Explicit beats implicit (label wrapping control) where possible; implicit is the fallback when a script generates no id. - Hidden-label options when the visual context makes the purpose obvious (search field beside button): visually-hidden label (1px clip technique, not display:none - that hides it from screen readers too), aria-label, aria-labelledby. Avoid title attribute (inconsistent screen-reader support). - aria-label/labelledby give nothing to visual users; use only when the purpose is visually clear. - Label position: right of radios/checkboxes, left of or above other fields. Above the field reduces horizontal scrolling for low-vision and mobile users. - Use HTML5 input types (number, date) so mobile shows the right virtual keyboard. Most users need visible labels; do not drop them for style. - Image buttons: label via alt (functional image, see alt tree). - WCAG hooks: 1.3.1, 2.4.6 (AA), 3.3.2, 4.1.2.

WAI form instructions

Source: https://www.w3.org/WAI/tutorials/forms/instructions/ - Screen readers switch to Forms Mode inside form elements and read only form controls; overall instructions must sit before the form element or they are skipped. - Overall instructions first: how required fields are marked, date formats, password rules, where per-field help lives. - In-label instructions (e.g. "Expiration date (MM/YYYY)") are the most reliable across browsers and assistive tech. - Outside-label options: aria-labelledby and aria-describedby (announced after the label; not fully supported everywhere, e.g. Braille displays). Keep for/id anyway. - Placeholders are not labels: screen readers do not treat them as labels, they vanish on input, and default placeholder styling usually fails WCAG contrast. Fix with::placeholder { color: #767676; opacity: 1; } as the minimum example, and keep a real label (see: never placeholder-only).

WAI form validation

Source: https://www.w3.org/WAI/tutorials/forms/validation/ - Use the required attribute (browsers set aria-required automatically) but keep "(required)" visible in the label text for older browsers and non-AT users. - HTML5 types (email, url, number, range, date, time) give validation plus better controls (pickers, mobile keyboards). maxlength/min/max/steps constrain input. pattern takes regexes for custom formats (e.g. plates, postcodes). - Be forgiving: accept multiple phone-number formats and liberal input; validate on the server too - client-side validation is UX, not security. - Let users review and correct before critical actions. Require confirmation for irreversible actions (delete dialogs, transfer checkboxes, order summaries). Provide undo where possible (trash folders, undo-send windows).

WAI form notifications

Source: https://www.w3.org/WAI/tutorials/forms/notifications/ - Overall feedback on submit: update the main heading ("There are 2 errors in this form") and the page title (screen readers hear it first); dialogs are the obtrusive option - a custom dialog must match native alert keyboard/setting behaviour. - Error list at top of page, before the form, distinctive heading; each item references the control's label, describes the error plainly, says how to fix it (repeat format requirements), and in-page links to the control. AJAX forms: put the list in a prominent container with a status role; associate fields with messages via aria-describedby. - In-line feedback: combine message plus visual cue (check/icon plus border colour - never colour alone; a low-contrast accent fails as an error colour anyway). Set focus to the first error on submit. - During typing: instant checks (username availability) help but must not overwhelm; binary success/error messages as you type. - Success messages matter: confirm task completion, not just absence of errors.

WAI accessible tables

Source: https://www.w3.org/WAI/tutorials/tables/ - Data tables only (never layout). Header cells in th, data cells in td; assistive tech reads one cell at a time and announces the associated headers, so the header-data relationship must be programmatic. - Complexity ladder: one header row/column -> plain th/td; two headers -> scope="col"/"row"; irregular headers spanning groups -> colgroup/rowgroup scope values; multi-level headers -> id on headers plus headers attribute on data cells. - caption identifies the table's topic (use in most cases); summary gives orientation for complex tables. - Structural markup also enables user restyling and list rendering of table data. - Markup is often lost in format conversions (CMS to PDF etc.); check exports.

WAI image types detail

Sources: https://www.w3.org/WAI/tutorials/images/decorative/, https://www.w3.org/WAI/tutorials/images/functional/, https://www.w3.org/WAI/tutorials/images/textual/ - Decorative: null alt (alt="") so screen readers skip them; never omit the alt attribute. Decorative-by-judgment cases: borders/spacers, supplementary to link text, eye-candy, already described by adjacent text. Prefer CSS background images for decoration. role=presentation is less supported than null alt. Exception: an image marking a thematic break should use hr, not an img. - Functional: alt conveys the action, not the picture - "print this page" not "printer", "search" not "magnifying lens", "W3C home" not "W3C logo". Missing alt on functional images is worst case: screen readers announce the file name or URL. Logo images are exempt from image-of-text contrast/size requirements. - Redundancy rule: icon plus text link where the icon adds nothing -> null alt; icon adding info (opens new window, file format PDF) -> alt states that info. - Images of text: use real CSS-styled text instead (resizable, restylable); when an image must be used, alt is the text itself, decorative effects ignored.

Infinite scrolling vs pagination

Source: https://www.nngroup.com/articles/infinite-scrolling/ (Loranger 2014) - Infinite scroll suits flat, constantly streaming content and serendipitous browsing (social feeds, gift browsing); it removes pagination mechanics and keeps engagement. - Bad for goal-oriented tasks: finding specific content, comparing options, ecommerce filters, backtracking to a previously found item ("page 3" is memorable, "somewhere down an endless page" is not). - Psychological costs for task-driven users: information abyss, no sense of completion, choice paralysis - users view but do not act (lower conversions). - Pagination gives a beginning and an end: users anticipate effort, feel completion, control continuation. - Desktop offense: infinite scroll breaks the scrollbar's length signal; users still use it to gauge remaining effort.

Accordions: when they work

Source: https://www.nngroup.com/articles/accordions-complex-content/ (Loranger 2014) - Upsides: less scrolling, headings act as a mini-IA, page looks less daunting, better than within-page links (those break the hypertext mental model). - Downsides: interaction cost per heading (clicks are currency; wasted clicks breed defiance), hidden content gets ignored, extra accessibility coding effort, bad printing. - Three scrolling myths busted: users do scroll when content is relevant and scannable; 20% of attention goes below the fold (80% above); people handle lots of content if it is written for the web. - Avoid accordions when the audience needs most or all of the content - relevance trumps page length. Extremely long pages may need several digestible pages instead, not accordions and not chopped tiny pages. - Use accordions when people need only a few key pieces of one page (FAQs), and on mobile where long pages defeat scrolling. Always allow multiple sections open and remember their state.

Progressive and staged disclosure

Source: https://www.nngroup.com/articles/progressive-disclosure/ (Nielsen 2006) - Progressive disclosure: show the few most important options first, defer specialized ones on request (print dialog pattern). Improves learnability, efficiency, error rate; initial display itself signals what is important. - Two things to get right: the split (everything frequently needed must be up front; frequency-of-use data helps) and the progression (obvious mechanics, label with strong information scent - "Advanced options", not mystery). - Beyond 2-3 levels, simplify or chunk advanced features into card-sorted groups. Multiple paths to secondary displays add complexity; avoid. - Staged disclosure (wizards) differs: linear steps in task order, users visit every step. Works when steps are independent; fails when interdependent. Hotel-booking study: room/price/date comparison belongs on one screen, address/payment on a later one - a 2-screen compromise beat both 1-screen and 5-screen designs.

Toggle switches

Source: https://www.nngroup.com/articles/toggle-switch-guidelines/ (Kendrick 2018) - Toggle = digital on/off for system states and preferences, one option, always a default. Choice table: radios for one-of-many, checkboxes for independent multi, single checkbox or toggle for binary - toggles differ by taking effect immediately. - Immediate results are the contract: if the change cannot apply at once (long forms with a Submit), use radios or a single checkbox instead. A toggle that does nothing visibly is a failure (United app example). - Labels: short, key words first, describe the on state, never neutral ("Include non-maternity items?" fails the read-aloud "on/off" test). - Visual design: slider metaphor with movement and high-contrast state colour (mind cultural colour meanings and contrast - a low-contrast accent on dark grey fails). State descriptors: use both "off" and "on" at the correct sides; one word alone reads as a label. - Implement consistently per platform; mixing toggles and radios on identical-looking pages breaks users (Chase example).

Checkboxes vs radio buttons

Source: https://www.nngroup.com/articles/checkboxes-vs-radio-buttons/ (Nielsen 2004) - Rules unchanged since 1984: radios = mutually exclusive list, exactly one; checkboxes = independent options, zero to all; stand-alone checkbox = single on/off. - Marketing opt-ins: single short question with an unchecked-by-default checkbox. Don't ask the same thing twice in positive and negative forms. - Standard visuals: square with checkmark, circle with dot. Group visually, subhead long checkbox lists, lay out vertically one per line. - Positive active wording for checkbox labels; if the unchecked state is unclear, use two radios instead. - Radios beat dropdowns (options permanently visible, lower cognitive load). Always give radios a default; add a "None" option when refraining must be possible; options must be comprehensive ("retired" example) or add "Other". - Click target includes the label (Fitts's Law; label element). - Settings widgets, not action buttons: changes apply on OK/Proceed; Back discards them; Back-then-Forward acts as undo-redo.

Sliders

Source: https://www.nngroup.com/articles/gui-slider-controls/ (Harley 2015) - Selecting a precise value with a slider demands good motor skills; on touch devices (one hand, walking) it is unrealistic, and for motor-impaired users it can be near impossible. - Use sliders only when an approximate value suffices (Kayak departure hour); when precision matters (weight entry, ratings), use steppers, direct input or tappable stars instead. Abnormal scales and tiny increments (0.1 lb) compound the failure; don't start from a random value. - The wider or denser the range, the harder precise selection gets. - Visual design: put increment labels and the current value ABOVE the track, where the thumb won't cover them (Airbnb right, Brilliant Earth wrong).

Tabs, used right

Source: https://www.nngroup.com/articles/tabs-used-right/ (Sunwall 2024, reviewed Sep 2026) - Tab anatomy: list, short label, panel, selection indicator(s). Use when content has clear few groupings, concise labels, unequal importance (default tab gets the attention - nondefault tabs must be supplemental), and users never need to compare across tabs (tab-switching taxes short-term memory). - Overflowing tab lists become carousels - hidden tabs lose discoverability. Fewer is better. - Two types: navigation tabs (dissimilar content, page loads, top of viewport) and in-page tabs (similar content, instant, one always selected). Never mix them in one control; a link masquerading as a tab (Behance example) breaks the model. When both appear in one product, style them differently. - Selection indicators: common region, line (not 1px low-contrast), font styling, size, icon. Use at least TWO indicators - critical with only two tabs. Unselected tabs must stay readable (MongoDB's faded labels failed contrast). - One row only: stacking tab rows destroys spatial memory (Amazon 2000 example). - Tabs vs accordions: accordions win on mobile and for short FAQ-like chunks; tabs on desktop when labels are short.

Modal vs nonmodal dialogs

Source: https://www.nngroup.com/articles/modal-nonmodal-dialog/ (Fessenden 2017) - Modal = system enters a special mode; main content disabled until the dialog is addressed. Nonmodal leaves the main content interactive. - Costs of modals: compulsory immediate attention, workflow interruption with re-immersion cost, forgotten task context, an extra dismiss-goal, blocked background content. So they fail for noncritical activities. - Legitimate uses: (1) important warnings that prevent irreversible errors (unsaved work, Gmail's forgotten-attachment reminder); (2) requesting info critical to continue a user-initiated process (Etsy login before saving a favorite); (3) fragmenting complex workflows (wizards - but show progress); (4) asking info that significantly reduces later work (Zillow's agent question - relevant interruptions only). - Never for nonessential, off-task content: newsletter signup modals earn visceral disdain, and wolf-crying trains users to dismiss all future dialogs unread. GoodHousekeeping's 3-second full-screen signup modal is the anti-example. - Implementation hooks: use native dialog with showModal, entry animation via @starting-style, aria-describedby for error text.

Tooltips

Source: https://www.nngroup.com/articles/tooltip-guidelines/ (Kendrick 2019) - Tooltip = brief user-triggered message on mouse hover or keyboard hover; desktop-only (no hover on touch - use popup tips there: tap to open, tap elsewhere to close). Auto-appearing feature tours are NOT tooltips. - Never for task-critical info: password requirements in a tooltip fail (Amtrak). Good use: explaining an unusual field or an unlabeled icon (Alibaba's search-by-image camera icon). - Content is microcontent: brief, helpful, never redundant (a tooltip repeating the button label is pollution). No tooltip beats a useless tooltip. - Must support keyboard hover as well as mouse hover (accessibility). - Use arrows when several elements sit close together; keep tooltips consistent across the site or users never discover them; moderate contrast against the background; position so they don't cover the content they explain. - The self-test: if the info is necessary to complete a task, put it on the page; tooltips are a fail-safe, not a crutch for extreme minimalism. Label icons instead of tooltip-ing them where possible.

Cards as a UI component

Source: https://www.nngroup.com/articles/cards-component/ (Laubheimer 2016) - Definition: container for a few short, related pieces of information, roughly playing-card sized, a linked short representation of one conceptual unit. Border + distinct background + slight shadow as clickability signifier; whole card is the tap target (Fitts). - Four properties: groups info; presents a summary that links to details; resembles a physical card; flexible layout (variable height, usually fixed width). - Psychology basis: the common-regions principle (items inside a boundary are perceived as grouped) can trump Gestalt proximity - a border groups items even when spacing says otherwise. - When cards are WRONG: (1) users searching for a specific item - cards de-emphasise ranking and are less scannable than a vertical list (fixed predictable positions scan faster); (2) comparing options - eyetracking shows users bounce back and forth between cards; keep visual treatment consistent for comparison; (3) homogeneous collections (photo galleries, similar blog posts) - a plain grid or list serves better. Cards excel for heterogeneous collections (dashboards, social feeds). - Distinct from the 1990s hypertext deck-of-cards model (full-screen pages, e.g. iOS Weather city swiping).

Error-message guidelines

Source: https://www.nngroup.com/articles/error-message-guidelines/ (Neusesser & Sunwall 2023; extends heuristic #9) - Visibility: message adjacent to the error's source; bold high-contrast red + icon + border (never color or animation alone - ~350M people with color-vision deficiency); match severity to the pattern (toast/banner for "good to know", modal only for severe blocking errors); never show errors prematurely (a field losing focus while empty is exploration, not an error) - but DO give real-time inline guidance for error-prone inputs like passwords. - Communication: plain human language, no codes/jargon (404 pages are the classic violator); precisely describe the actual problem; offer a remedy, not just the problem; positive tone, never blame the user (avoid "invalid/illegal/incorrect"); no humor for recurring errors. - Efficiency: safeguard against likely mistakes (the forgotten-attachment warning pattern); preserve the user's input for correction; suggest concrete fixes the user can click (ZIP->city); link to brief explanations when needed. - Total failure: a rare catastrophic outage can carry apology + novelty (Twitter's Fail Whale) because of negativity bias and peak-end.

Comparison tables

Source: https://www.nngroup.com/articles/comparison-tables/ (Moran & Dykes 2024) - For compensatory decisions (weighing pros/cons across attributes, usually <5-7 alternatives). Noncompensatory decisions (one knockout factor, e.g. price cap) are served by filters/facets, not tables. - Skip the table when items are not mutually exclusive, simple, cheap/replaceable, or unique/hard to compare. - Static tables for <=5 preselected offerings; dynamic (user picks items) for larger sets - compare buttons/checkboxes as secondary actions on listing pages, or direct-manipulation compare modes. - Best practices: max ~5 items (2 on mobile; clearly communicate limits; allow removing items); CONSISTENT content across items is the biggest failure (missing metadata kills the table; no cutesy values like Zip/Zero/Zilch/Nada); standard layout options-as-columns, attributes-as-rows, row labels left; short cell text not sentences; light color coding with adequate contrast; clear row separation; STICKY column headers on long attribute lists; meaningful attributes translated to concrete terms (mAh -> "1.2 iPhone charges", oz -> "weight of an egg"), tooltips for jargon; give control - collapsible rows, "highlight differences" toggle, simplified at-a-glance table + detailed view.

Visualizing links

Source: https://www.nngroup.com/articles/guidelines-for-visualizing-links/ (Nielsen 2004, editor's note March 2026) - 2026 editor's note supersedes the 2004 absolutes: underlines no longer required by default; the standard is WCAG 1.4.1 - color must not be the ONLY link cue; technique G183 = 3:1 contrast between link and body text + extra indicator on hover/focus. - Still-valid rules: never underline non-link text; never use the link color for non-link text; avoid blue for non-links (strongest clickability affordance); don't bold on hover (relayout); distinguish visited/unvisited as shades of the same hue, unvisited more vivid; link titles help predict destinations. - Underlines remain essential where link color is red/green (color-blindness) or for low-vision-heavy audiences. Menus/nav lists may skip underlines when the region is obviously navigation.

APG keyboard/ARIA mechanics for the common widgets

Modal dialog

Source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/ - Content outside a modal is inert AND visually obscured - aria-modal="true" only when both are true. Focus moves inside on open (first focusable, or a static top element with tabindex="-1" for long/structured content; focus the least destructive action for irreversible steps); Tab/Shift+Tab wrap inside; Escape closes; focus returns to the invoking element on close. Include a visible close button in the tab sequence. Native <dialog> gives much of this.

Tabs

Source: https://www.w3.org/WAI/ARIA/apg/patterns/tabs/ - tablist/tab/tabpanel roles; tab gets aria-controls->panel, panel gets aria-labelledby->tab, active tab aria-selected="true". Arrow keys move between tabs (wrap around); activation follows focus ONLY if panels render without latency (preloaded), else manual activation with Space/Enter. Horizontal tablists must not hijack Up/Down arrows (page scroll). Tabpanel with no focusable content gets tabindex="0".

Menu button

Source: https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/ - Button with aria-haspopup="menu" and aria-expanded. Enter/Space/Down opens with focus on first item; Up opens with focus on last. Menu internals per the Menu and Menubar pattern.

Disclosure / show-hide

Source: https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/ - Button (role button) + controlled region; aria-expanded toggles, optional aria-controls; Enter/Space toggles. The FAQ/accordion primitive - pairs with NN/g accordion guidance and progressive disclosure.

Tooltip

Source: https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/ (pattern still work-in-progress per W3C) - Appears on hover OR keyboard focus; Escape dismisses; focus stays on the trigger; tooltip itself never receives focus (if it must contain focusable content, use a non-modal dialog instead); role tooltip + aria-describedby on the trigger; stays open while the cursor is over trigger OR tooltip. Matches 's tooltip timing (delay first, instant neighbours).

Accordion (APG)

Source: https://www.w3.org/WAI/ARIA/apg/patterns/accordion/ - Header = a button INSIDE a heading element (heading level per page IA; button is the heading's only child). aria-expanded + aria-controls on the button; aria-disabled="true" on the header whose panel can't be collapsed. Enter/Space toggles; all focusable elements stay in the page Tab sequence. - Panels may get role region + aria-labelledby ONLY for small accordions - skip it above ~6 simultaneously expandable panels (landmark proliferation).

Combobox (APG)

Source: https://www.w3.org/WAI/ARIA/apg/patterns/combobox/ - Input + popup (listbox/grid/tree/dialog). Select-only vs editable; four autocomplete modes: none, list-manual, list-automatic (first suggestion pre-selected), list-inline (completion string shown inline, highlighted). - Keyboard: Down Arrow into popup (past the auto-selected suggestion); Escape dismisses WITHOUT changing the prior value (vs listbox, where moving changes value with no undo); Enter accepts; Alt+Down opens without moving focus. Never let JS capture the browser's native text-editing keys. Popup and its descendants stay OUT of the page Tab sequence. - Combobox beats menu-button when the chosen value must be visible/copyable; beats listbox for exploratory choice with Escape-undo.

Switch (APG)

Source: https://www.w3.org/WAI/ARIA/apg/patterns/switch/ - Strictly binary (no mixed state - that's checkbox/toggle-button territory). role switch + aria-checked (or native input[type=checkbox] with checked). Space (optionally Enter) toggles. CRITICAL: the label must not change when state changes. Choose switch vs checkbox by which semantics read better aloud ("Lights switch on" vs form-question "checked").

Table (APG)

Source: https://www.w3.org/WAI/ARIA/apg/patterns/table/ - table = STATIC structure, not a widget: cells are not focusable; each widget inside a table is its own Tab stop - if there are many, use grid (composite widget) instead. Prefer native HTML table. Sortable columns: aria-sort on the sorted header cell. aria-colcount/rowcount + colindex/rowindex when rows/columns can be hidden; rowspan/colspan ARIA equivalents exist.

Carousel (APG)

Source: https://www.w3.org/WAI/ARIA/apg/patterns/carousel/ - Required controls: previous/next buttons; auto-rotating carousels MUST have a stop/restart rotation control as the FIRST Tab stop inside, and rotation stops on keyboard focus or hover, never resumes by itself. Off-screen slides must be truly hidden (off-screen display confuses screen readers). - Container role region/group + aria-roledescription="carousel"; slides role group + aria-roledescription="slide"; name slides "3 of 10" if no better label; aria-live="polite" on the slide wrapper only when NOT auto-rotating (off when rotating). Rotation control label flips between "Stop/Start slide rotation" (no aria-pressed). Slide pickers: tabs pattern (best) > grouped buttons (each a Tab stop, worst).

Checkbox (APG)

Source: https://www.w3.org/WAI/ARIA/apg/patterns/checkbox/ - Dual-state and tri-state (aria-checked="mixed") variants; tri-state drives group select-all (some implementations restore the previous partial selection on a third activation). Space toggles. Groups get role group + aria-labelledby (or fieldset/legend natively); descriptions via aria-describedby.

Radio group (APG)

Source: https://www.w3.org/WAI/ARIA/apg/patterns/radio/ - One Tab stop per group (roving tabindex or aria-activedescendant): Tab in lands on the checked radio (first if none checked); arrows MOVE AND CHECK together (wrapping); Space checks. Exception inside toolbars: arrows only move focus, Space/Enter checks - because toolbar arrows must navigate without side effects. - Note the browser divergence: native Shift+Tab into an unchecked group can land on the LAST radio.

Slider (APG)

Source: https://www.w3.org/WAI/ARIA/apg/patterns/slider/ - Keys: arrows = one step, Page Up/Down = larger steps, Home/End = min/max. Focus on the thumb. aria-valuenow/min/max always; aria-valuetext when the number isn't human-friendly ("Monday", "3:45 of 12:30"); aria-orientation for vertical. - W3C warning: some touch-based assistive tech can't operate ARIA sliders (gesture-to-key synthesis is a new convention) - test on touch devices before production; native input[type=range] is the safer default.

Alert (APG)

Source: https://www.w3.org/WAI/ARIA/apg/patterns/alert/ - role alert = important message that does NOT interrupt: announced automatically by screen readers when DYNAMICALLY rendered (alerts present at page load are not announced). Must never move keyboard focus (that's alertdialog's job); must not auto-disappear (WCAG 2.2.3); keep frequency low (WCAG 2.2.4 - interruption fatigue).

WCAG 2.2 - the 9 new success criteria

Source: https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/ (WCAG 2.2 became a W3C Recommendation 5 Oct 2023; 4.1.1 Parsing removed) - 2.4.11 Focus Not Obscured (AA): a focused component must be at least PARTIALLY visible - sticky headers/footers/banners must not cover it. 2.4.12 (AAA): fully visible. - 2.4.13 Focus Appearance (AAA): indicator area at least a 2 CSS px perimeter of the component, 3:1 contrast between focused/unfocused pixels. - 2.5.7 Dragging Movements (AA): every drag action needs a single-pointer alternative (e.g. up/down buttons for reordering) unless dragging is essential. - 2.5.8 Target Size Minimum (AA): 24x24 CSS px, with exceptions: spacing (24px circles around undersized targets don't intersect), equivalent control elsewhere, inline text links, user-agent-sized, essential. (WCAG floor; NN/g's 1cm touch rule remains the better target.) - 3.2.6 Consistent Help (A): help mechanisms (contact, chat, self-help) appear in the same relative order across pages. - 3.3.7 Redundant Entry (A): info entered earlier in the process must be auto-populated or selectable - never ask twice (security re-entry excepted). - 3.3.8 Accessible Authentication Minimum (AA): no cognitive-function test (memory, puzzle, transcription) at login unless an alternative exists, a mechanism assists, or it's object recognition/personal content. 3.3.9 (AAA) removes those two exceptions.

WCAG Understanding 2.4.7 Focus Visible + 2.4.11 Focus Not Obscured

Sources: https://www.w3.org/WAI/WCAG22/Understanding/focus-visible and https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum - 2.4.7 (AA): at least one mode of operation where the keyboard focus indicator is visible and not time-limited. User agents may show the indicator only for keyboard use (:focus-visible, C45) - the author must not remove it (outline:0 without replacement fails; F55 scripts that steal focus fail). Focus indicators are non-text content, so 1.4.11's 3:1 applies to them; C40 = two-colour indicator to survive any background. AAA sibling: 2.4.13 Focus Appearance (covered area). - 2.4.11 (AA, WCAG 2.2): when a component receives keyboard focus it must not be ENTIRELY hidden by author-created content. WCAG 2.2 deep reads: 2.5.8, 2.5.7, 3.3.7, 3.3.8, 3.2.6

Inclusive Components deep reads

Source site: https://inclusive-components.design/ (Heydon Pickering, 2017-18; still the reference implementation discussions) - Cards: no <card> element or ARIA card pattern - build from lists (<li> per card so screen readers enumerate) with one heading per card (same level, flat hierarchy). NN/g heuristic deep dives #1, #2, #4 + the #5 case study

Sources: nngroup.com/articles/{visibility-system-status, match-system-real-world, consistency-and-standards, error-prevention} - #1 Visibility of system status (Harley 2018): know the state to control it (gulf of evaluation). Just write a clear permanent label. Tooltips are a LAST resort when space is truly scarce (WYSIWYG toolbars); the "no space" excuse dissolves if labels are treated as important from the start. - Two distinct patterns. Inclusive Components: tabbed interfaces

Source: https://inclusive-components.design/tabbed-interfaces/ (Pickering 2017) - Embryonic tabs = table of contents + same-page links + sections (TOC -> tablist, links -> tabs, sections -> panels). CSS:target can hide non-target sections but that is material dishonesty (Keith): a TOC must not LOOK like tabs, and site nav must never be styled as tabs - users then expect tab behaviors (arrow keys, no page load). - True tabs are a desktop paradigm justified only by keyboard ergonomics: arrow keys move between tabs (inactive tabs tabindex="-1"), Tab key skips INTO the panel ("Tab is not for tabs"), Shift+Tab returns to the selected tab. Progressive disclosure: Nielsen's original criteria

Source: https://www.nngroup.com/articles/progressive-disclosure/ (Nielsen 2006; deepens) - The dilemma it solves: users want BOTH power (everybody's a special case) and simplicity. Show few important options initially; disclose specialized options on request. Print dialog is the canonical case (and has grown bloated - a cautionary drift). - The initial display itself communicates importance: novices avoid mistakes and wasted attention; experts scan less. Improves learnability, efficiency, error rate - three of the five usability components. Fears of a limiting mental model are groundless per research. - The two failure modes: (1) wrong split - everything frequently needed must be up front (determine via task analysis, field studies, frequency-of-use stats + observational testing since page hits can be navigational mistakes); (2) unclear progression mechanics - obvious button placement and labels with strong information scent. - Beyond two disclosure levels usability collapses; if you need three, simplify or chunk the advanced set (card sorting) and test both common and advanced tasks. - Progressive vs staged table: hierarchical vs linear navigation; initial display = core features vs first-in-sequence; most users never visit secondary displays in progressive, everyone visits every step in staged. Staged fails when steps are interdependent (hotel case: room/price/date comparison belongs on ONE screen; address/payment deferred - 2 screens beat both 1 and 5).

Never open dialogs without a user action; if you must, restore focus manually on dismiss. - JS-free close: form method="dialog" (or formmethod="dialog" on the button) - submits nothing, preserves entered data, sets dialog.returnValue to the button's name. The open attribute (or.open property) marks an open-but-NON-modal dialog; having open in the HTML on load keeps the dialog working without JS. - role=dialog is implicit; use role="alertdialog" for confirmations requiring response + give it an accessible name (aria-labelledby pointing at visible text). - Styling gotcha: dialog color/background come from UA CanvasText/Canvas (Safari: black/white) - color is inherited from dialog, not body/:root; background-color is not inherited. - Inert: the global inert attribute disables an element and its descendants (modal dialogs get inertness for free).

Calm UI rules

Source: maxschmitt.me/posts/calm (Max Schmitt, Sept 2026). - THE 2 RULES: (1) NO CASCADING LOADING STATES - keep the save-button's loading state until the background list has refetched; sequential spinners (button -> skeleton -> list) read as chaos, one sustained state reads as calm. (2) NO TOASTS - instead show the action take effect (the item appears in the list); a toast is a confirmation of something the user should just SEE. - BONUS RULES: (3) no toasts for errors either - toasts appear far from the click point on large screens and vanish, leaving users confused; put errors where the action happened. (4) Pin height-changing modals to the TOP - a centered modal that grows an error message shifts the submit button vertically; top-pinned keeps the button still. (5) Enter submits - free in React via <form onSubmit> instead of <button onClick>. (6) Focus the first input when a dialog opens - saves a click every single time. - Meta: the article itself is the teaching format - every rule has an interactive before/after you can feel. Points onward to Jakub Krehel ("The invisible side of design engineering") and Emil Kowalski.
