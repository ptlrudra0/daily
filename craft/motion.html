Motion Craft

Easing, duration, choreography, scroll systems, page transitions and micro-interactions, with the recipes behind them.

Motion rules

Source: Emil Kowalski, emilkowal.ski/ui/7-practical-animation-tips; Josh Comeau animation guides; Material motion docs.

  • Press feedback: scale 0.97 on:active. (source)
  • Never animate from scale(0); start 0.9+ (his demo uses 0.93); a deflated balloon still has a shape.
  • Tooltips: delay before the first, no delay and no animation for the neighbours (Radix and Base UI do this; Base UI via data-instant with 0ms).
  • Easing is the most important part. Enter/exit = ease-out (fast start feels responsive); at identical 300ms an ease-in dropdown feels slower. Built-in CSS curves are weak; use custom cubic-beziers (he recommends easings.co).
  • Origin-aware popovers: set transform-origin to the trigger (Radix var --radix-dropdown-menu-content-transform-origin, Base UI var --transform-origin), not centre.
  • Keep UI animation fast, about 300ms or less; section 6 of the page.

Easing and duration table (source: github.com/emilkowalski/skills animate guide; licence unverified - treat as reference)

Easing: enter/exit = ease-out; move/morph on screen = ease-in-out; hover/colour = ease; constant motion (marquee, progress) = linear. Never ease-in on UI. Curves: --ease-out cubic-bezier(0.23,1,0.32,1); --ease-in-out cubic-bezier(0.77,0,0.175,1); --ease-drawer cubic-bezier(0.32,0.72,0,1). More at easing.dev / easings.co. Duration: press 100-160ms; tooltips 125-200ms; dropdown 150-250ms; modal/drawer 200-500ms; marketing/explanatory can be longer. Springs for drag/interruptible/alive motion: {type:spring,duration:0.5,bounce:0.2}; bounce 0.1-0.3 max. Transitions (not keyframes) for anything triggered rapidly (they retarget). Exit the way it entered. Respect reduced motion and gate hover effects to pointer devices.

Performance budget for heavy/motion sites: Core Web Vitals

  • Thresholds, measured at the 75th percentile of page loads, mobile and desktop separately: LCP good <=2.5s (poor >4.0s); INP good <=200ms, needs improvement <=500ms, poor >500ms; CLS good <=0.1 (poor >0.25). A page passes only if all three pass. Sources: https://web.dev/articles/vitals, https://web.dev/articles/lcp, https://web.dev/articles/inp, https://web.dev/articles/optimize-cls (all fetched and read in part).
  • INP is about the next frame painting after a tap, not the eventual result: give instant visual feedback (accordion opens, button state) even if work continues.
  • Common CLS causes: images/embeds/ads without dimensions, injected content, web fonts. Fits the font-serving advice: reserve space, mind font swap.
  • Lab vs field mismatch is normal: Lighthouse sees only the load, field data (CrUX) sees the whole visit.
  • Implication for WebGL/preloader sites (Lusion class): a preloader hides LCP but costs the first impression; keep a static hero as fallback..

Reduced motion

  • prefers-reduced-motion (values no-preference, reduce) exposes the OS setting; Baseline widely available since Jan 2020. Sources: https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion, https://web.dev/articles/prefers-reduced-motion (Steiner).
  • Why: parallax and large scale/pan effects are vestibular triggers (dizziness, nausea, migraine); for some users reducing motion is medical. Parallax is called out because background and foreground move at different rates.
  • Three roles of motion on the web: feedback, perceived-speed tricks (skeletons, low-quality previews), decoration. Reduced mode should drop decoration and autoplay first, keep feedback (a state change can be a fade or colour change instead of a fly/scale).
  • Check it from CSS and from JS (matchMedia) - the web.dev page covers both.

WCAG motion criteria

  • 2.2.2 Pause, Stop, Hide: moving/blinking/scrolling content that starts automatically, lasts over 5 seconds and sits alongside other content needs a user mechanism to pause, stop or hide it; auto-updating content needs pause/hide or frequency control; exceptions where essential. Applies to auto-advancing carousels, looping background video, tickers. https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html
  • 2.3.3 Animation from Interactions: motion animation triggered by interaction can be disabled unless essential. Intent text names parallax and scroll-triggered movement; accepted ways: avoid it, give an off control, or honour the OS reduce-motion setting. Normal scroll movement itself is allowed. 2.3.3 covers user-triggered motion, 2.2.2 covers automatic motion; some animation fails both. https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html
  • Conformance levels: A for 2.2.2, AAA for 2.3.3.
  • Closes the carousel discussion: 2.2.2 is the criterion that makes auto-advance need a pause control.

content-visibility, contain, contain-intrinsic-size

Sources: https://developer.mozilla.org/en-US/docs/Web/CSS/content-visibility, https://developer.mozilla.org/en-US/docs/Web/CSS/contain, https://developer.mozilla.org/en-US/docs/Web/CSS/contain-intrinsic-size - content-visibility: Baseline 2024 (Sept 2024, some parts vary). auto lets the browser skip rendering off-screen sections; big LCP/rendering win on long pages. Forces containment. - contain: Baseline widely available since Mar 2022. Isolates a DOM subtree's layout/style/paint/size for cheaper recalcs. - contain-intrinsic-size: Baseline widely available since Sept 2023. Placeholder size for a skipped element, so scrollbars stay stable while content-visibility auto defers real layout (no CLS - see CWV notes).

Response-time limits

Source: https://www.nngroup.com/articles/website-response-times/ (Nielsen 2010; limits from 1993, ~40-year-old human-factors research) - Three human-perception thresholds: 0.1s = feels instantaneous, caused by the user (needed for direct manipulation); 1s = flow of thought stays seamless (needed for good navigation); 10s = attention limit, users start thinking about other things and often leave. - Even a few seconds' repeated delay makes uncommitted users give up - NN/g: can lose half your sales. - Slow causes change, effect is constant: big images in 1997, slow servers and overly fancy widgets in 2010. Users do not care why. - Slowness becomes a brand value: in a recall study users spontaneously complained about slow sites. - Eyetracking case: an 8s-to-load promo slideshow got only 1% of viewing time from the user who saw the delay vs 20% from the user who looked after it rendered. Anything over ~1s render is effectively invisible. - 0.1s shaved off response time produced a measurable conversion lift; same finding across decades.

INP - Interaction to Next Paint

Source: https://web.dev/articles/inp (Wagner & Pollard, updated Sep 2025) - INP is the stable Core Web Vital for responsiveness, FID's successor. It observes EVERY click/tap/keypress during the visit and reports the longest interaction latency (one outlier ignored per 50 interactions), p75 across page views. Thresholds: good <=200ms, needs work 200-500ms, poor >500ms. - Why it exists: 90% of time on a page happens AFTER load, so load metrics miss the real experience. INP measures time until the next paint is blocked, not the full async completion - the earliest visual feedback moment. - Three phases per interaction: input delay (main thread busy), processing duration (event handlers), presentation delay (until the frame paints). Hover, zoom, scroll are not observed. - Field data (CrUX/RUM) beats lab; TBT is the lab proxy only. Long tasks blocking the main thread are the classic cause (users click repeatedly, thinking it's broken). - Maps to perception thresholds: 200ms good INP sits between Nielsen's 0.1s instant and Doherty's 400ms.

prefers-reduced-motion deep dive

Source: https://web.dev/articles/prefers-reduced-motion (Thomas Steiner) - Values: no-preference (falsey) and reduce. The robust pattern is opt-IN to motion: animate only under @media (prefers-reduced-motion: no-preference), so older browsers and opted-out users get the still version; JS check via matchMedia("(prefers-reduced-motion: reduce)"). - Why: vestibular disorders - parallax (background moving at a different rate than foreground) and big zoom/reveal effects can cause dizziness, nausea, migraines; for these users reducing motion is a medical necessity, not a taste. - Reduce does not mean none: keep motion that carries meaning (feedback that an action was received), cut decorative motion (animated gradients, autoplay video, parallax).

LCP - Largest Contentful Paint

Source: https://web.dev/articles/lcp (Walton & Pollard, updated Sep 2025) - Core Web Vital for perceived load speed: render time of the largest visible image, text block, or video relative to navigation start. Includes previous-page unload, redirects, connection setup, TTFB. - Thresholds (75th percentile, mobile and desktop): good <=2.5s, poor >4s. - Candidates: img, image-in-svg, video poster, url background, block-level text containers. Excluded as non-contentful: opacity:0, full-viewport (likely background), low-entropy placeholders. Size = visible size only (clipped overflow, margins, padding, border excluded); resized images count the smaller of visible vs intrinsic size. - Reporting updates as larger elements render; stops on first user interaction (tap/scroll/keypress). Text waiting on a web font and unloaded images do not count yet - font strategy and image priority move LCP directly.

CLS - Cumulative Layout Shift

Source: https://web.dev/articles/cls (Walton, updated Aug 2025) - Largest burst of unexpected layout-shift scores over the page lifecycle. A burst/session window: shifts <1s apart, max 5s window. Thresholds: good <=0.1, poor >0.25 (75th percentile). - Score = impact fraction x distance fraction. Impact = union of an element's visible area before/after as a fraction of viewport; distance = greatest move / largest viewport dimension. - Shifts within 500ms of discrete input (tap/click/keypress) get hadRecentInput and are excluded - scroll, drag, pinch are NOT discrete input, so scroll-linked shifts count. - Fix causes: reserve space (width/height or aspect-ratio on media), never inject content above existing content, show a loading indicator in pre-made space for slow requests. Animate with transform (scale/translate), never width/height/top/left. Respect prefers-reduced-motion.

Optimize LCP - the four subparts

Source: https://web.dev/articles/optimize-lcp (Pollard, updated 2025) - Break LCP into four non-overlapping subparts: TTFB, resource load delay, resource load duration, element render delay. Ideal budget: TTFB ~40%, load delay <10%, load duration ~40%, render delay <10%. Delays near zero is the tell; optimizing one part can just shift time into another (e.g. compressing the image does nothing if render waits on JS). - Diagnostics: use CrUX field data first (RUM or PageSpeed Insights; lab tools can disagree with reality). Large TTFB-to-FCP delta = render-blocking assets or heavy client-side rendering; large FCP-to-LCP delta = LCP resource not in the initial HTML or competing work. - Kill resource load delay: put the LCP resource in the HTML, fetchpriority="high" on the hero image, preload where needed; never lazy-load the LCP image. Cut load duration: AVIF/WebP, sized correctly. Kill render delay: reduce/inline render-blocking CSS, defer JS, watch long tasks; if the LCP is text, font-display: anything but auto/block keeps text visible without waiting on the font.

Optimize CLS - the four causes and fixes

Source: https://web.dev/articles/optimize-cls (Walton & Pollard) - The four common causes: images without dimensions, ads/embeds/iframes without dimensions, dynamically injected content, web fonts. - Images: always width + height attributes (browsers derive the default aspect-ratio from them) or CSS aspect-ratio; combine with width:100%;height:auto. - Fonts: FOUT and FOIT both shift layout because the fallback metrics differ. font-display: optional avoids re-layout entirely (web font only used if ready at first layout). Always name a matching generic fallback ("Google Sans", sans-serif - bare "Google Sans" falls back to Times). Match fallback metrics with size-adjust / ascent-override / descent-override / line-gap-override; preload critical fonts so they make first paint. - Dynamic content: never inject content above existing content except as a user-initiated response; reserve space with a placeholder or skeleton UI; for banners/cookie notices prefer overlay (out of document flow). - Lab vs field: CrUX measures the full page life including post-load shifts (lazy-loaded content mid-scroll, transitions slower than the 500ms input grace). Lighthouse shifted-elements audits show the elements affected, not necessarily the cause - look above them.

Optimize INP - the three interaction subparts

Source: https://web.dev/articles/optimize-inp (Pollard, updated Sep 2025) - Every interaction = input delay (user acts -> event callbacks start) + processing duration (callbacks run) + presentation delay (next frame paints). Field data (RUM, else CrUX via PSI) first, then reproduce in lab; interact during page load too, when the main thread is busiest. - Input delay: worst during startup script evaluation (parse/compile/execute). Reduce JS, code-split. - Processing: do as little as possible in the callback. Only render-critical work before the next frame; defer the rest (the text-editor example: update the textbox, then requestAnimationFrame(() => setTimeout(...)) for word count, spellcheck, save). Yield often; indiscriminate yielding beats none. - Presentation delay: avoid layout thrashing (reading layout after writing), keep the DOM small; content-visibility lazy-renders off-screen content to cut rendering work both at load and during interactions. - INP is page-level: each iframe has its own main thread but slow iframe interactions count toward the page INP.

Optimize long tasks - 50ms is the wall

Source: https://web.dev/articles/optimize-long-tasks (Walton, updated 2024) - A task is any discrete unit of browser work; JS runs to completion and the main thread does one task at a time. A task >50ms is a long task; the excess is its blocking period. Users feel a page as broken when interactions queue behind long tasks. - Breaking work into small functions does NOT break the task - saveSettings calling five functions is still one monolithic task. Tasks only split at yield points. - scheduler.yield (await it) is the dedicated yielding API: its continuation is prioritized - the rest of the current task resumes before other queued tasks start, unlike setTimeout which queues behind. Not universal yet; feature-detect globalThis.scheduler?.yield and fall back to a Promise-wrapped setTimeout (or the scheduler-polyfill).

Font best practices - loading, delivery, rendering

Source: https://web.dev/articles/font-best-practices (Hempenius & Pollard) - Fonts affect FCP/LCP (delayed text render) and CLS (swap with mismatched fallback metrics). - Loading: @font-face alone downloads NOTHING - a font file is requested only when used styling matches. So trim unused CSS: dead styles mean fonts discovered late or never... and unstyled @font-face blocks discovered early do nothing. Inline critical font declarations in for earliest discovery. Google Fonts: use (includes preconnect), not @import. - Preload with care: it ignores unicode-range and steals bandwidth from other resources; prefer fixing discovery order over papering over it with preload. - Delivery: self-hosting removes the third-party connection but only wins behind a CDN + HTTP/2 (Web Almanac found third-party fonts often render faster); WOFF2 only (Brotli, ~30% smaller than WOFF); subset with unicode-range (Latin fonts run 100-1000 glyphs, CJK 10k+; Google Fonts subsets by script automatically). - Pair with the CLS font fixes and LCP text rule.

Emil Kowalski: Great Animations

Source: https://emilkowal.ski/ui/great-animations - Natural: the physical world never swaps states instantly; springs (stiffness/damping/mass) read as alive. Instant state changes feel artificial. - Fast: under ~300ms, ease-out as the default (fast start = feels responsive, smooth settle). Fast spinners make the same wait feel shorter - perceived performance is UX. - Purposeful: pace animations; every animation you add dilutes the rest. Never animate keyboard-initiated actions - they repeat hundreds of times a day and animation makes them feel slow (Raycast has no enter animation and feels right). - Performant: animate transform + opacity (composite only; margin/padding trigger layout+paint+composite). If the main thread is busy, rAF-driven JS animation drops frames - use CSS transitions/animations or WAAPI, which are hardware-accelerated (real case: Vercel dashboard tab indicator fixed by moving from Shared Layout Animation to CSS). - Interruptible: users change their minds mid-animation; CSS transitions reverse smoothly mid-flight (this is a reason to prefer transitions over @keyframes animations for state changes). - Accessible: honour prefers-reduced-motion; swap motion for opacity fades.

Motion design in depth

Purpose first

Uses: feedback (action received), state change, spatial metaphor/navigation, signifier (what is interactive), perceived speed (skeletons/placeholders, web.dev). Attention-grabbing is fine, attention-hijacking is not. The more often seen, the subtler and shorter. Excess motion is an accessibility issue: flashing and hard colour cuts (seizures); parallax, carousel auto-advance, scroll-jacking (vestibular).

Anatomy of an animation

Trigger (click, hover, scroll position, gesture, load) -> elements -> transformed properties (opacity, position, scale, colour, shape, blur, rotation) -> duration -> easing. Moving objects: arc paths feel more natural than straight diagonals; long ones annoy on repeat. Opacity changes on many elements can be costly: prefer transform + opacity on few elements; avoid animating layout properties.

Timing

Feedback (toggle/checkbox) ~100ms; modal/large change 200-300ms; most animations 100-400ms; 500ms+ drags. Marketing/story moments may be longer (hero reveals 600-1200ms are fine once, not repeatedly) [Emil: marketing can be longer]. The easing table and curves are above.

Choreography

Stagger siblings 30-80ms, lead with the hero object, secondary follows, one direction of travel per scene, same easing family across the site, elements enter from where they logically came from and leave the way they came. Overlap start of the next motion before the previous ends. One orchestrated entrance per view, not everything animating.

Scroll

CSS scroll-driven animations (animation-timeline: scroll/view) now native (joshwcomeau.com/animation/scroll-driven-animations, Apr 2026): use for reveals, progress bars, parallax-lite with no JS. For pinned scenes and scrubbing use GSAP ScrollTrigger + Lenis. Keep scroll natural: no scroll-jacking that fights the wheel; keep native scroll position/anchors working.

Page and view transitions

Microinteractions

Trigger -> rules -> feedback -> loops/modes (Dan Saffer model, Q). Examples: button press 0.97, toggle with thumb+colour+halo in 100ms, hamburger-to-X morph, copy confirmation, form field validation, cursor-reactive hero. One signature microinteraction repeated consistently = interaction language.

Reduced motion

@media (prefers-reduced-motion: reduce) removes non-essential movement: no parallax, no zoom, no autoplay loops, crossfade instead of slide, disable smooth-scroll hijack (do not init Lenis). Test with the OS setting. Provide pause control for any auto-moving content longer than 5s.

Smooth, never stiff: every state change eased, nav transitions animated, scroll buttery; but budgets: <300ms UI, one hero moment per section; glow behind buttons, no motion-for-motion's-sake.

Additional recipes

  • Material 3 tokens: Standard cubic-bezier(0.2,0,0,1); standard decelerate (0,0,0,1); standard accelerate (0.3,0,1,1); emphasized decelerate (0.05,0.7,0.1,1); emphasized accelerate (0.3,0,0.8,0.15). Durations: short 50/100/150/200ms, medium 250/300/350/400ms, long 450/500ms+ (large expressive transitions, usually emphasized easing). Selection controls 200ms standard; FAB-to-sheet 400ms emphasized. Note: Material says its expressive update moves to a spring physics system and the easing/duration system is no longer maintained, so treat the tokens as reference values, springs for interactive gesture motion.
  • Microinteractions: trigger-feedback pairs; trigger = user action or system state change; feedback = small, narrow, contextual (usually visual) change next to the trigger. Jobs: show system status, prevent errors, communicate brand. Static always-present elements and multi-step flows are not microinteractions; a button with no feedback is not one.

Disney's 12 principles applied to UI

Squash and stretch, anticipation (prepare the viewer: slight pull-back before a drawer opens), staging (direct attention to the one thing that matters: ONE hero), straight-ahead vs pose-to-pose, follow-through and overlapping action (parts settle at different times: stagger), slow in/slow out (easing), arcs (natural paths), secondary action (supports the main action, never competes), timing, exaggeration (sparingly), solid drawing (consistent volume/depth), appeal. Web mapping: easing = slow in/out; stagger = overlap; arcs = curved travel paths (NN/g); staging = the single focal moment per section; anticipation = small pre-motion on hover/press. Keep exaggeration and squash for playful brands only.

NN/g animation timing and scroll fading

Source 1: Executing UX Animations: Duration and Motion Characteristics https://www.nngroup.com/articles/animation-duration/ - Most UI animations 100-500 ms depending on complexity and distance. Simple feedback (toggle, checkbox) about 100 ms. Big changes (modal into view) 200-300 ms. "At 500ms, animations start to feel like a real drag". 100-400 ms is the usual range, 400 ms only for big movements on large screens. Entering animations a little longer than exiting (e.g. 300 ms in, 200-250 ms out). Small changes (250 vs 300 ms) feel different, so test. Opacity changes on many elements at once can be expensive for performance. Specify animations as timelines in ms with easing, not frames. Source 2: Scroll Fading 101 (Sara Paul, Dec 8 2023) https://www.nngroup.com/articles/scroll-fading-101/ (qualitative usability study) - Fade-in rate: experiment 100-400 ms; too slow and users skip text, too fast and they don't notice. - Fade content in once and keep it persistent so users can scroll back and re-read. - Fade one element type at a time (text or images, not both): Apple.com did this and had the best efficiency and comprehension in the study. - Reduce excessive whitespace between faded sections (proximity) and use closure so people keep scrolling instead of thinking the page ended. Build rules derived: UI feedback 100-300 ms; scroll reveals 100-400 ms, once, one element type at a time; cinematic hero sequences are the exception, and their duration should be a conscious choice. Baymard: free research hub exists (450+ free articles, product page studies e.g. https://baymard.com/blog/current-state-ecommerce-product-page-ux).

Kowalski animation standards (emilkowalski/skills, MIT)

Condensed reference; cite the repo for full text.

Should it animate (frequency table): 100+/day (keyboard, palette) = never animate; tens/day (hovers, list nav) = remove or drastically reduce; occasional (modals, toasts) = standard; rare (onboarding, celebrations) = delight allowed. Valid purposes: spatial consistency, state, explanation, feedback, preventing jarring change. "Looks cool" on frequent elements is not valid.

Easing decision order: enter/exit → ease-out; on-screen move/morph → ease-in-out; hover/colour → ease; constant (marquee) → linear; default ease-out. NEVER ease-in on UI (delays the watched moment). Built-ins too weak: --ease-out cubic-bezier(0.23,1,0.32,1); --ease-in-out cubic-bezier(0.77,0,0.175,1); --ease-drawer cubic-bezier(0.32,0.72,0,1) (iOS-like).

Duration: button press 100-160ms; tooltips 125-200; dropdowns 150-250; modals/drawers 200-500. Rule: UI stays under 300ms. Faster spinners make load FEEL faster; skip tooltip delay+animation after first hover.

Physicality: never scale(0) — start scale(0.9-0.97)+opacity 0. Popovers scale from trigger (transform-origin var; modals exempt, keep center). Press feedback scale(0.97):active 160ms ease-out.

Springs: for drag/momentum/alive elements/interruptible gestures; Apple-style config {duration:0.5, bounce:0.2}; bounce 0.1-0.3 max; springs keep velocity when interrupted (keyframes restart from zero — that's why transitions beat keyframes for rapidly retriggered UI).

Gestures: momentum dismissal by velocity (>~0.11 px/ms) not distance threshold; damp past boundaries (friction over hard stops); pointer capture on drag start; ignore extra touch points mid-drag.

Stagger: 30-80ms between items, never block interaction. A11y: prefers-reduced-motion = fewer/gentler, not zero (keep opacity, drop transforms); gate hover motion behind (hover:hover) and (pointer:fine). Cohesion: match motion to component personality; easing/duration/name in harmony (Sonner example). Debug: 2-5x slow-mo, frame-by-frame DevTools, real devices for gestures, fresh eyes next day.

Disney 12 principles (Johnston & Thomas, The Illusion of Life 1981)

With UI transfer per principle. See also Kowalski standards above (they rhyme: slow-in-slow-out = ease-in-out; timing = duration tables). 1. Squash & stretch — weight/flexibility; VOLUME MUST NOT CHANGE (stretch vertically → contract horizontally). UI: press states, playful brand moments only; keep scale changes volume-compensated or tiny. 2. Anticipation — prepare the audience before the action (wind-back before pitch). UI: hover states pre-signal the click; a panel that nudges before sliding; skeletons anticipate content. 3. Staging — "presentation of any idea so that it is completely and unmistakably clear"; placement, light/shadow, camera; avoid unnecessary detail. UI: this IS visual hierarchy — one focal point per view. 4. Straight-ahead vs pose-to-pose — fluid improvisation vs planned keyframes; combine. UI: pose-to-pose = keyframed hero sequences; straight-ahead = physics/spring simulations for gestures. 5. Follow-through & overlapping action — loose parts keep moving after the core stops; parts move at different rates; "drag" = parts catch up late. Moving hold: even still characters breathe. UI: staggered children (cards trail the container), secondary motion settling after primary; subtle idle animation keeps hero alive. 6. Slow in & slow out — more frames near the extremes; acceleration/deceleration. UI: the basis of all UI easing; Kowalski's ease-out rule refines it for enter/exit. 7. Arc — natural motion follows arcs; mechanical motion goes straight; breaking arc for no reason reads erratic. UI: drag paths and element entrances should curve slightly, not teleport in straight lines (except deliberately mechanical/cyber styles). 8. Secondary action — adds life but must EMPHASIZE not distract; if it competes, cut it or place it at the start/end. UI: icon motion inside a button, ambient background drift — keep below the main action's salience. 9. Timing — frame count = speed = weight: light reacts faster than heavy. UI: timing communicates mass — heavy modals slower, micro-feedback fast (matches Kowalski duration table). 10. Exaggeration — reality presented in wilder form; restraint + balance across elements. UI: overshoot on springs is controlled exaggeration; one exaggerated moment per screen max. 11. Solid drawing — volume, weight, balance, light/shadow; avoid "twins" (mirrored symmetry reads lifeless). UI: asymmetric layouts feel alive; perfect mirror symmetry feels static (interesting tension with Reber symmetry-fluency — symmetry aids PROCESSING, asymmetry aids LIFE; use symmetry in structure, asymmetry in composition). 12. Appeal — charisma, not necessarily sympathy; villains can appeal. UI: brand personality must be interesting, not merely nice.

Lenis docs verified

  • Runs on NATIVE scroll (wraps browser scroll): position:sticky, anchor links and accessibility keep working — the key difference from transform-hijack smooth scrollers.
  • Defaults: duration 1.2s, easing = exponential-out t => Math.min(1, 1.001 - Math.pow(2,-10t)); lerp overrides duration. syncTouch option mimics touch scroll (unstable on iOS<16).

Source: https://www.nngroup.com/articles/animation-usability/ (Harley, 2014). - Three real goals: explain a change, add whimsy, look modern. Codrops "Atelier UI" tutorial

Source: tympanus.net/codrops/2026/10/21/atelier-ui-webgl-dom/ (Jérémie Nallet). - THE MIXED-DOM/WEBGL PROBLEM SET, solved one at a time (the article's real value is the problem inventory): 1. JITTER: native scroll moves the DOM first, WebGL follows a frame later. Fix: Lenis smooth scroll. 2. DOUBLE CLOCK: Lenis and the canvas each run their own frame loop -> tiny lag. Fix: ONE clock - Motion's frame loop drives both (lenis.raf on frame.update, R3F advance on frame.postRender). 3. CONTEXT LIMIT: one canvas per effect hits the WebGL context cap. Fix: a single fixed full-screen behind the page (WebglProvider); every WebGL component portals its meshes into it. 4. SCROLL SYNC: calling getBoundingClientRect per frame per element is too expensive. Fix: measure each element's position ONCE (and on resize); per frame the plane only subtracts the current scroll. 5. CAMERA CONFLICT: a 3D scene that moves the camera disturbs every other plane. Fix: WebglScene gives the scene its own camera scoped to a container (track prop), pointer events remapped for raycasting. Alternative rejected: 1-unit=1px camera (forces all 3D to be sized in pixels) - keep R3F's default camera, let each primitive do its own pixel conversion. - ACCESSIBILITY-FIRST WEBGL TEXT: keeps the real text in the DOM at opacity: 0 (screen readers + SEO intact), reads its COMPUTED styles (font, size, weight, letter-spacing, color), paints it line-by-line on an offscreen 2D canvas, uses that as the texture of a plane. The WebGL version is a pixel-faithful doppelganger, not a replacement. - PAGE TRANSITIONS THAT NEVER POP: TransitionLink stops navigation, plays the cover animation, loads the new route behind it, and WAITS FOR THE NEW PAGE'S WEBGL ASSETS to finish before revealing - no texture pop-in; back/forward go through the same steps; reduced-motion degrades the pixel transition to a simple fade. - DISTRIBUTION AS CRAFT: shadcn-registry distribution (copy-the-code, own every piece), install via paste-to-agent prompt, shadcn CLI, or MCP server - each ships with a skill file that teaches the agent how to set the component up. Sources: /2026/10/08/building-parallel-page-transitions-with-gsap-and-react-router/ (Ismael Martinez), /2026/09/24/custom-shaped-cursor-trail/ (Bautista Berto). - PARALLEL VS SEQUENTIAL TRANSITIONS: the taxonomy settled. Sequential = old page leaves, THEN new page enters (Barba/Swup default, Next.js App Router constraint - his next-transition-router package works around it by freezing navigation, animating, then navigating). Parallel = BOTH pages mounted simultaneously, outgoing+incoming animated on ONE GSAP timeline (Swup Parallel plugin, Barba sync:true, Nuxt default mode, Taxi removeOldContent). View Transition API achieves similar visuals but is STATE-oriented (outgoing = static snapshot, incoming = live); the React+GSAP approach is TIMELINE-oriented (both pages live, coordinated). React Router key: useOutlet lets you "hold" the current page node while mounting the new one - no manual head/script reloading. Caveat he states honestly: transitions fight browser/framework performance work (Next instant pages) and affect accessibility. Persistent elements (R3F scene) live outside the Outlet but still join the choreography. Engine packaged as npm lib "hyperkinetic" (alpha). - CUSTOM-SHAPED CURSOR TRAIL (Three.js WebGPU + TSL): upgrades the ubiquitous radial-blob trail. Architecture: a 200x200 float DataTexture = the cursor's MEMORY (grid cells remember position history + velocity); channels: R = direction x, G = direction y, B = speed. Velocity measured PER FRAME (vs prev position), not per event - stays in sync with the render loop. THE BRUSH IS THE ONLY SHAPE DECISION: force = (1 - dist/brushRadius)^falloff decides the mark; the default circular fade returns the boring blob - swap ~10 lines (diagonal stripes, any shape function) and the whole mark changes. DECAY doctrine: every cell dies 1->0 via k = decay^(dt*60); "I love decays. They make things feel natural and smooth... that is what takes a cursor trail from working to feeling right." Cost trick: bound the cell loop to the brush radius so a bigger grid costs nothing. A source texture (a word) can mask the ink; trail colored by speed. Philosophy line: "combining what you learn from different places to reach a solution nobody else would."

Codrops tutorial: Astro + GSAP pixel transition & pixel reveal

Source: tympanus.net/codrops/2026/10/09/architecture-studio-astro-gsap/ - Kaisei Sadatoki, architecture-studio landing page. Design hook: Kode Mono's pixel look inspires the whole motion system. - PIXEL SECTION TRANSITION recipe: a 25-col x 6-row CSS Grid of JS-generated divs overlaid at a section boundary (height ~24vw), each cell initially the CURRENT section's bg color. Per-row flip probability array (e.g. [0.1, 0.2, 0.5, 0.7, 1, 1]) makes cells flip to the NEXT section's color top-to-bottom; gsap.utils.shuffle picks ~6 cells to flip to an ACCENT color instead - "to make the animation feel less mechanical." Animate with gsap.to(backgroundColor, duration 0.05, stagger each 0.003 from "random", ease none) scrubbed by ScrollTrigger (start "top bottom", end "top 20%"). Gotcha: margin 0 -1px -1px 0 on cells + overflow hidden on wrapper, or hairline grid seams show. - CANVAS PIXEL REVEAL for images: hidden + visible . Draw the image onto a temp canvas at low resolution and scale up to the display canvas with image smoothing off. Resolution driven by state.progress: pixels = 18 + (naturalWidth - 18) * pow(progress, 2.5) - start at 18px wide, ease back to full res; GSAP scrubs progress 0->1. The pow(2.5) curve makes the reveal resolve quickly at first then slow into sharpness. - PATTERN: pixel-as-motif - pick one structural unit from the typeface/brand (here the monospace pixel) and let it organize both the transitions and the reveals. One motif, many motions (cf. StringTune motif-systems).
